Objectifs du tutoriel

Dans ce tutoriel pratique, nous allons explorer comment transformer un pipeline de données statique en un moteur ETL flexible grâce aux paramètres. En suivant un scénario concret d'ingestion depuis une API, vous apprendrez à rendre vos flux de données adaptables à différents contextes sans modifier leur logique interne.

Pourquoi paramétriser les Pipelines de données ?

Les pipelines de données dans Microsoft Fabric permettent d'orchestrer des flux de travail complexes : extraction, transformation et chargement de données depuis diverses sources.

Afin qu'un un pipeline soit véritablement dynamique et donc réutilisable, il n'est pas suffisant de configurer des valeurs fixes en dur dans la définition du pipeline.

Et c'est là qu'interviennent les paramètres. En effet, ils permettent de rendre les pipelines dynamiques et modulaires sans toucher à la logique sous-jacente.

Dans ce tutoriel, nous allons apprendre à :

  • Créer et configurer des paramètres dans un pipeline Fabric
  • Les utiliser dans vos activités (Copy Data, Dataflow, Notebook, etc.)
  • Transmettre des valeurs dynamiquement lors de l'exécution
  • Appliquer les bonnes pratiques pour maintenir des pipelines clairs et évolutifs

Scénario

Pour illustrer l'utilisation des paramètres dans un pipeline ETL de données paramétré , nous allons suivre le scénario suivant :

  1. Créer un pipeline de données paramétré
  2. Extrait des données depuis une API RESTful externe ([REST Countries](https://restcountries.com/))
  3. Transforme ces données avec un notebook Spark
  4. Charge les données transformées dans une table SQL

Le paramètre permettra d'exécuter le pipeline avec différents noms de pays.

Avant de commencer l'implémentation du pipeline ETL paramétré, nous allons mettre en place l'infrastructure nécessaire à la réalisation de ce tutoriel :

  1. Nous procéderons d'abord à la création d'un Workspace dédié dans Microsoft Fabric, qui servira de conteneur pour l'ensemble de nos ressources et garantira une isolation propre de notre projet.
  2. À l'intérieur de cet espace de travail, nous créerons ensuite un Lakehouse qui jouera un rôle central dans notre architecture : il accueillera à la fois les fichiers bruts extraits depuis l'API externe (dans le répertoire Files/raw/clients/) et les données transformées issues du notebook Spark (dans Files/transformed/clients/).
  3. Enfin, nous mettrons en place une base de données SQL (via l'endpoint SQL du lakehouse) qui contiendra notre table de destination clients_final ainsi que la procédure stockée usp_Charger_Clients responsable du chargement final des données.

L'ensemble de ces éléments constitue l'écosystème technique indispensable pour illustrer concrètement chacune des étapes de notre tutoriel, depuis l'extraction paramétrée jusqu'au chargement final en passant par les transformations.

Définition des Paramètres dans un Pipeline

Définition d'un paramètre dans un Notebook

La définition d'un paramètre dans un notebook Microsoft Fabric suit une convention spécifique qui permet une intégration fluide avec les Pipelines.

Pour créer un paramètre, il faut dédier une cellule en haut du notebook et y déclarer les variables avec des valeurs par défaut. L'élément crucial est ensuite d'activer le tag "paramètres" sur cette cellule.

Cette action signale à Fabric que cette cellule contient des paramètres pouvant être surchargés lors d'une exécution via un Pipeline. Ainsi, lorsque le Notebook est appelé par une activité de Pipeline, les valeurs définies dynamiquement dans ce dernier remplacent automatiquement les valeurs par défaut de la cellule taguée, permettant au code des cellules suivantes d'utiliser ces variables sans aucune modification.

Voyons comment créer ce type de cellule pour paramètre, en suivant les étapes

  1. Passer la pointeur de la souros dans le coi gaiche de la cellule et cliquer sur les trois points
  2. Dans les options roposées, chosiir Toggle parameter cell

Creation d'une procédure stockée

Pour poursuivre l'illustration d'utilisation de paramètre de Pipeline, nous allons mettre en place une Procédure Stockée en T-SQL. Comme la requête de création d'un table, depuis l'interface de la base de données SQL, ouvrir une requête vide et copier-coller le code suivant : 

CREATE PROCEDURE [dbo].[InsertCountry]
@name NVARCHAR(64)
AS
BEGIN

DECLARE @filePath   NVARCHAR(250);
SET @filePath = CONCAT('‹path_abfss›', @name, '.csv');

DECLARE @sqlCommand NVARCHAR(MAX);

SET @sqlCommand = 'INSERT INTO [dbo].[Countries]
SELECT  
   [Pays] ,
   [Capital] ,
   [Region] ,
   [Subregion] ,
   [Flags] 
FROM OPENROWSET(
   BULK ''' + @filePath + ''', 
   FORMAT = ''CSV'' , 
   FIRSTROW = 2,     
   FIELDTERMINATOR = '',''
) WITH ([Pays] NVARCHAR(16), [Capital] NVARCHAR(16), 
        [Region] NVARCHAR(16), [Subregion] NVARCHAR(16),
        [Flags] NVARCHAR(32)) AS tt ;
'

EXECUTE sp_executesql @sqlCommand;

END

Cette procédure stockée, nommée [dbo].[InsertCountry], a pour objectif d'automatiser l'ingestion de données à partir de fichiers CSV créés par le notebook et stockés dans le lakehouse. L'ingestion va se faire dans la table [dbo].[Countries] de la base de données que nous avons cré précédemment.

La procédure attend un paramètre d'entrée unique, @name, qui correspond au nom du fichier du fichier CSV à charger et qui sera piloté par le paramètre du Pipeline @pipeline().parameters.name.

À partir de ce paramètre, le chemin d'accès complet @filePath vers le fichier source est construit en concaténant un préfixe de chemin ABFSS ‹path_abfss› avec la valeur du paramètre et l'extension ".csv".

Cette procédure est idéale pour être appelée depuis une activité Stored Procedure d'un Pipeline Data Factory, où elle pourrait être itérée pour charger plusieurs fichiers CSV correspondant à différents pays, chacun étant passé dynamiquement comme paramètre du Pipeline.

Mise en place d'une activité Stored procedure dans le Pipeline de Données

Ajout d'une activité Stored procedure au Pipeline

L'intégration d'une activité Stored Procedure dans un Pipeline permet d'exécuter des procédures stockées directement depuis une base de données source ou de destination.

  1. Ouvrir l'interface du Pipeline pour afficher le canevas du data workflow
  2. Aller dans le menu Activities
  3. Cliquer sur l'activité Stored Procedure depuis la palette des activités

Activité Stored procedure - Menu General

Dans un Pipeline Microsoft Fabric, le menu General d'une activité Stored Procedure constitue la première étape de configuration, accessible dès que l'activité est ajoutée au canevas. On y renseigne tout d'abord un nom explicite pour l'activité, qui permettra de l'identifier clairement dans le flux d'exécution du Pipeline. Ce menu offre également la possibilité d'ajouter une description détaillée, une bonne pratique pour documenter le rôle de l'étape. Pour cela, suivre les étapes suivantes :

  1. Aller dans l'onglet General
  2. Dans le champ Name, entrer un nom explicite pour cette activité

Activité Stored procedure - Menu Settings

Dans un Pipeline Microsoft Fabric, le menu Settings d'une activité Stored Procedure est l'endroit crucial où l'on connecte l'activité à la base de données cible et où l'on spécifie la logique à exécuter.

  1. Aller dans l'onglet Settings
  2. Depuis le menu déroulant Connection, sélectionner la connection qui est utilisé par ce Workspace
  3. Depuis le menu déroulant SQL Database, sélectionner la base de données SQL que nous avons créé pour ce tutoriel
  4. Dans le menu déroulant Stored procedure name, sélectionner la procédure stockée que nous avons créé
  5. Sélectioner le menu Stored procedure parameters qui va permettre d'ajouter les variables en entrées attendues par la procédure stockée
  6. Cliquer sur + New pour ajouter une variable
  7. Dans le champ Name, entrer le nom de la variable tel que inscrite dans la définiton de la procédure stockée
  8. Dans le menu déroulant Type, sélectionner le type du paramètre. Ici le paramètre est de type String
  9. Dans le champ Value, entrer la valeur dynamique issue des paramètres du Pipeline : 
    @pipeline().parameters.name

Exécition d'un Pipeline

Pour lier efficacement les activités au sein d’un Pipeline dans Microsoft Fabric, il est essentiel de comprendre le flux de contrôle et les dépendances entre les différentes tâches. Dans l’interface de la Data Factory, on établit ces liaisons en connectant visuellement les activités via leur sortie. Par exemple, après l'activité Copy data, on peut lui rattacher l'activité Notebook en faisant glisser la poignée verte (ou "success") depuis la première activité vers la seconde. Cela crée une dépendance explicite : l’activité Notebook ne s’exécutera que si l’activité de copie se termine avec succès.
