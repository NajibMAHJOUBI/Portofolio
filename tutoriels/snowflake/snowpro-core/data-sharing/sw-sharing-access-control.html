Snowflake Data Sharing Privileges

✅ 1. Private Sharing dans Snowsight

Snowsight permet d'explorer et gérer les bases partagées (shared databases) provenant d'un partage direct ou d'un listing.

Ce qu'un utilisateur peut faire dans Snowsight :
  • Visualiser si la base est issue d'un share.
  • Voir le provider, le type de partage, le nom du share ou listing.
  • Supprimer (DROP) la base consommée (cela ne supprime pas le share dans le compte du provider).
  • Gérer les privilèges locaux sur la base consommée (RBAC classique).
Ce qui est important pour SnowPro :
  • Snowsight indique clairement la provenance : direct share, Marketplace listing, data exchange, listing privé.
  • Une shared database est toujours en lecture seule côté consumer.
  • La suppression de la base côté consumer ne supprime pas le share chez le provider.

✅ 2. Data Sharing côté Provider (Using SQL with Data Shares)

This topic describes the tasks for a data provider creating and configuring shares, adding consumer accounts, and maintaining shares.

✔ 1. Création du SHARE

CREATE SHARE my_share;

✔ 2. Ajout d'objets au share via GRANT TO SHARE

GRANT USAGE ON DATABASE mydb TO SHARE my_share;
GRANT USAGE ON SCHEMA mydb.public TO SHARE my_share;
GRANT SELECT ON TABLE mydb.public.sales TO SHARE my_share;
Granting privileges effectively adds the objects to the share.

✔ 3. Ajout des consumer accounts

ALTER SHARE my_share ADD ACCOUNT = <account_identifier>;
A share is available immediately to a consumer when you add that consumer's account.
✔ Notes importantes
  • Un share peut contenir des objets provenant de plusieurs bases, si elles sont toutes dans le même compte.
    A share can include data from multiple databases.
  • Le partage est temps réel : New and modified rows are available immediately to consumers.
  • Attention : recréer un objet (DROP puis CREATE) fait qu'il n'est plus automatiquement dans le share.
    A new object created or recreated is not automatically available.

✅ 3. Sécurité et privilèges liés aux Shares

GRANT … TO SHARE grants access privileges for supported objects; this effectively adds the objects to the share.

✔ Privilèges utilisables avec TO SHARE

  • DATABASE : USAGE, REFERENCE_USAGE (REFERENCE_USAGE requis pour les vues sécurisées multi-databases).
  • SCHEMA : USAGE
  • TABLE / VIEW / EXTERNAL TABLE / ICEBERG TABLE / DYNAMIC TABLE : SELECT
  • SECURE VIEW : SELECT (impossible sur vue non sécurisée)
    The SELECT privilege on views can only be granted on secure views.
  • UDF secure : USAGE (pas possible sur UDF non‑secure)
    USAGE privilege can only be granted on secure UDFs.
  • TAG : READ
✔ Règles importantes pour SnowPro :
  • Un share ne peut recevoir USAGE que d'une seule database.
    The USAGE privilege on only a single database can be granted to a share.
  • Pour partager toutes les tables d'un schéma :
    GRANT SELECT ON ALL TABLES IN SCHEMA mydb.public TO SHARE my_share;
    Using an ALL clause, you can grant SELECT on all tables.
  • Les vues non‑secure ne peuvent pas être partagées.
  • Les UDF non‑secure ne peuvent pas être partagées.
  • Les UDF ne peuvent pas référencer des objets d'autres databases.
    Sharing a UDF that references objects from another database is not supported.

✅ 4. Le mécanisme côté Consumer (SQL)

Le consumer crée une base depuis un share :

CREATE DATABASE shared_db FROM SHARE provider_account.my_share;

Snowsight affichera ensuite : le nom du share, le provider, la provenance (direct share, listing).

La base est lecture seule.

✅ 5. Points clés pour SnowPro Core

🔹 PRIVATE SHARING via Snowsight

  • Snowsight permet de voir toutes les shared databases et leur provenance.
  • Les consumers gèrent uniquement le catalogue local de la shared database (nom, commentaire, suppression locale).

🔹 SHARING VIA SQL (Provider)

  • CREATE SHARE → GRANT … TO SHARE → ALTER SHARE ADD ACCOUNT.
  • Share = conteneur de métadonnées (zero-copy).
  • Partage immédiat une fois le compte ajouté.

🔹 PRIVILÈGES SUR LES SHARES

  • USAGE DB, USAGE schema, SELECT table/view.
  • Secure views obligatoires pour partager des vues.
  • UDF doivent être secure et ne pas référencer une autre DB.
  • REFERENCE_USAGE requis pour vues sécurisées multi‑databases.

🔹 LIMITATIONS

  • Recréer un objet (DROP/CREATE) ⇒ il sort automatiquement du share.
  • Un share ne contient qu'une seule database ayant le privilège USAGE.
