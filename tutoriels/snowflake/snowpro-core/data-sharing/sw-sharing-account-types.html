1. Introduction au Data Sharing Snowflake

Snowflake permet le partage de données sécurisé, sans copie, entre comptes Snowflake ou même avec des utilisateurs n'ayant pas de compte Snowflake.

✔ Concepts fondamentaux :

  • Zero-copy : les consommateurs accèdent aux données via un partage, sans duplication physique.
  • Le partage fonctionne en générant un share, qui regroupe les objets partagés (tables, views sécurisées, UDFs sécurisées, etc.).
  • Les consommateurs utilisent ces données comme des objets locaux (en lecture seule).

2. Data Providers & Data Consumers

Les objets répliqués ou partagés vers un autre compte sont accessibles en lecture seule.

✔ Provider (fournisseur)

  • Crée un share.
  • Y ajoute les objets (tables, vues, UDF sécurisées).
  • Donne accès soit :
    • à un consumer Snowflake existant,
    • à un reader account (si le client n'a pas de compte Snowflake).

✔ Consumer (consommateur)

  • Peut consulter les données du share sous forme de database partagée.
  • Ne peut pas modifier les objets sources → lecture seule.

3. Reader Accounts (lecture seule pour non‑clients Snowflake)

✔ Définition

Les Reader Accounts sont des comptes Snowflake gérés par le fournisseur, créés spécialement pour des consommateurs ne disposant pas de Snowflake.

Client Redirect permet de rediriger des connexions via un objet de connexion, et les consommateurs peuvent se connecter sans modifier la configuration. Ceci confirme que Snowflake peut exposer un accès à plusieurs comptes, concept utilisé dans Reader Accounts.

✔ Caractéristiques clés

  • Les Reader Accounts sont créés depuis le compte provider.
  • Le provider paye pour le compute consommé par les readers.
  • Le consumer via reader account consulte les données via :
    • une database partagée,
    • uniquement en lecture (pas de DML/DDL).
  • Le provider gère l'administration du compte reader (users, roles, warehouses).

✔ Utilisations typiques

  • Partage avec des partenaires n'ayant pas de Snowflake.
  • Diffusion de données à des clients externes.
  • Cas d'usage BI/analytics simple.

4. Objets pouvant être partagés

Les objets répliqués offrent un accès en lecture via des bases de données secondaires.

Par analogie directe avec Secure Data Sharing, les objets partageables comprennent :

  • Tables
  • Views sécurisées
  • UDF sécurisées
  • Sequences
  • File formats (selon contexte)
  • Listings (Marketplace)

5. Sécurité du Data Sharing

  • Snowflake ne copie jamais les données : le consumer lit une vue référencée dans le provider.
  • Isolation via RBAC.
  • Le provider reste propriétaire des données.

6. Gouvernance & privilèges

Pour créer un share :

  • Privilèges nécessaires sur les objets partagés.
  • Rôle système permettant CREATE SHARE.

Pour accéder à un share consommé :

  • CREATE DATABASE FROM SHARE
  • Usage limité au compte spécifié.

7. Billing / Facturation

Snowflake-managed serverless compute billing applies.

Ce principe est similaire pour les Reader Accounts : le provider paye pour les warehouses utilisés par les readers.

9. Processus standard de partage (vue d'ensemble)

  1. Provider crée un SHARE.
  2. Il ajoute objets (tables, views…) dans le SHARE.
  3. Il assigne le share à :
    • un compte consumer existant ou
    • un reader account.
  4. Consumer crée une database depuis le share.
  5. Il peut interroger les objets en lecture seule.

10. Points clés SnowPro Core à maîtriser

✔ Le partage Snowflake est zero-copy.

✔ Les données partagées sont toujours en lecture seule côté consumer.

✔ Le provider contrôle totalement le partage.

✔ Reader Accounts = Snowflake pour non‑clients, payé par le provider.

✔ Provider/Consumer = modèle central du sharing.

✔ Partager ≠ Répliquer : la réplication crée des copies synchronisées ; le sharing donne un accès aux objets source.
