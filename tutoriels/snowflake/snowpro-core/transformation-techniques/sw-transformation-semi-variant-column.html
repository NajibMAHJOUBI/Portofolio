1. Principes & limites — données semi‑structurées dans VARIANT

✔ Taille maximale d'une valeur VARIANT

Jusqu'à 128 MB non compressés (en pratique un peu moins à cause des surcharges internes et selon l'objet stocké).

✔ Quand stocker en VARIANT vs. aplatir ?

  • Si vos cas d'usage ne sont pas encore connus, Snowflake recommande de stocker d'abord dans VARIANT.
  • Pour des données "régulières" (ex. JSON avec chaînes/entiers), les besoins de stockage et la performance sont proches du relationnel.
  • Pour améliorer le pruning et réduire le stockage, aplatir (via colonnes relationnelles) si vos documents contiennent :
    • dates/timestamps (notamment non‑ISO 8601) représentés en chaînes
    • nombres encodés en chaînes
    • tableaux
  • Les valeurs non natives (dates dans JSON) stockées comme string dans VARIANT sont plus lentes à traiter et prennent plus d'espace que des colonnes typées.

✔ Approche de validation

Charger un échantillon dans VARIANT, FLATTEN les clés ciblées dans une table relationnelle, puis comparer les performances de vos requêtes typiques.

✔ Deux types de NULL dans le semi‑structuré :
  • SQL NULL : valeur manquante/inconnue (comme pour les types structurés).
  • JSON null (dit "VARIANT NULL") : stocké comme chaîne contenant "null" pour le distinguer de SQL NULL.

2. PARSE_JSON — conversion d'une chaîne JSON en VARIANT

But : interprète une chaîne d'entrée comme un document JSON et retourne un VARIANT (OBJECT/ARRAY au besoin). Pratique pour insérer du JSON inline ou transformer une colonne texte en JSON navigable.

✔ Syntaxe & paramètres

PARSE_JSON(<expr> [, '<parameter>'])
  • <expr> : chaîne contenant un JSON valide.
  • '<parameter>' : contrôle notamment la gestion des clés dupliquées :
    • 'd' = autoriser les clés dupliquées (la dernière valeur l'emporte)
    • 's' = strict (refus des doublons, par défaut).

✔ Comportements importants

  • Retourne VARIANT ; NULL en entrée → NULL en sortie.
  • Chaîne vide ou espaces uniquement → retourne NULL (pas d'erreur), pour laisser continuer le traitement.
  • La chaîne 'null' (littéral) devient un JSON null dans VARIANT (≠ SQL NULL).
  • Précision numérique : tente de préserver l'exactitude des décimaux (ex. 123.45 → NUMBER(5,2)), mais notation scientifique ou incompatibilités d'échelle → DOUBLE.
  • Types non natifs en JSON (DATE/TIME/TIMESTAMP/BINARY) doivent être représentés en chaînes.
  • Taille max de l'entrée : 64 MB compressés pour l'expression de PARSE_JSON.
Variante tolérante : TRY_PARSE_JSON(<expr> [, '<parameter>']) → retourne NULL si parsing en erreur (utile en ingestion "best‑effort").

3. Bonnes pratiques & pièges fréquents (SnowPro Core)

📌 Modéliser selon l'usage

Si vos analyses ciblent dates, champs numériques, filtres sur éléments d'ARRAY, envisagez un aplatissage sélectif pour les colonnes critiques → meilleur pruning et coûts moindres.

📌 Gérer les NULL correctement

Faites la différence entre SQL NULL et JSON null (dans VARIANT) → impacts sur filtres, agrégations et jointures.

📌 Encodage des dates/nombres

Dates/Timestamps en JSON = strings → préférez cast explicite à la lecture (et/ou colonnes relationnelles si réusage intensif). Chiffres encodés en chaînes = performance moindre ; privilégiez des nombres natifs ou des colonnes numériques.

📌 Clés dupliquées

Par défaut, PARSE_JSON est strict ('s') : une clé dupliquée lève une erreur ; vous pouvez autoriser via 'd' (la dernière valeur est conservée).

📌 Tolérance à l'erreur

En flux hétérogène (APIs, logs), préférez TRY_PARSE_JSON pour éviter l'échec de la requête en cas de JSON malformé.

📌 Taille & performance

Surveillez la taille de vos documents (VARIANT ≤ 128 MB non compressés) et l'entrée de PARSE_JSON (≤ 64 MB compressés). Les gros objets sont plus coûteux et limitent certaines opérations.

4. Exemples "type SnowPro"

A. Ingestion simple & navigation

-- Table avec une colonne VARIANT
CREATE OR REPLACE TABLE events (payload VARIANT);

-- Insertion à partir de JSON texte
INSERT INTO events VALUES
    (PARSE_JSON('{"user":{"id":101,"name":"Ana"},"ts":"2025-10-01T08:00:00Z","items":[{"sku":"A1","qty":2},{"sku":"B2","qty":1}]}'));

-- Lecture : accès par chemins + cast explicites
SELECT
    payload:user:id::NUMBER       AS user_id,
    payload:user:name::STRING     AS user_name,
    payload:ts::TIMESTAMP_TZ      AS ts_utc
FROM events;

PARSE_JSON → VARIANT ; accès par : et casts explicites.

B. Aplatir un tableau (FLATTEN) pour analyses

-- Extraire les items en lignes
SELECT
    e.payload:user:id::NUMBER       AS user_id,
    f.value:sku::STRING             AS sku,
    f.value:qty::NUMBER             AS qty
FROM events e,
LATERAL FLATTEN(input => e.payload:items) f;

Stratégie recommandée quand les ARRAY sont souvent parcourus : aplatir pour gagner en lisibilité et en performance selon les cas d'usage.

C. Résilience face aux "JSON imparfaits"

-- Tolérer des erreurs de parsing (ligne invalide => NULL)
SELECT TRY_PARSE_JSON(raw_line) AS parsed
FROM external_feed;

TRY_PARSE_JSON évite l'arrêt de pipeline en cas de malformation ponctuelle.

D. Gestion des clés dupliquées

-- Strict (défaut) : lève une erreur si un objet a des clés dupliquées
SELECT PARSE_JSON('{"k":1,"k":2}');   -- ERREUR (mode 's')

-- Permissif : conserve la dernière valeur
SELECT PARSE_JSON('{"k":1,"k":2}', 'd');   -- {"k":2}

Paramètre 'd' = duplicate keys allowed ; 's' = strict (défaut).

5. Check‑list d'examen (à mémoriser)

✔ VARIANT ≤ 128 MB non compressés ; PARSE_JSON ≤ 64 MB compressés.

✔ Stocker vs Aplatir : si beaucoup de dates/nombres/arrays, envisager aplatissage pour meilleur pruning et moins de stockage.

✔ NULL : distinguer SQL NULL et JSON null (VARIANT).

✔ PARSE_JSON : strict par défaut ('s'), 'd' tolère les clés dupliquées (dernière valeur).

✔ Numériques : décimaux préservés (ex. NUMBER(5,2)), scientifique → DOUBLE.

✔ Dates en JSON ⇒ strings ; cas d'usage intensifs ⇒ colonnes typées.

✔ TRY_PARSE_JSON pour l'ingestion robuste.
