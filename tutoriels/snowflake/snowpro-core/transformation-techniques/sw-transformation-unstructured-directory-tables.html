1. Qu'est‑ce qu'une Directory Table ?

Source : Directory Tables – Snowflake Documentation

“A directory table is an implicit object layered on a stage… conceptually similar to an external table because it stores file‑level metadata about the data files in the stage.”

✔ Caractéristiques clés :

  • Ce n'est pas un objet de base de données : pas de privilèges propres.
  • Associée directement à un stage (interne ou externe).
  • Fournit liste et métadonnées des fichiers :
    • nom du fichier
    • taille
    • timestamp dernière modification
    • URL Snowflake du fichier
✔ Comparable à : Une external table, mais sans schéma SQL, juste les métadonnées de fichiers.

2. Pourquoi utiliser une Directory Table ?

Snowflake liste trois usages centraux :

✔ 1. Lister tous les fichiers d'un stage

Accès SQL direct aux fichiers stockés dans un stage.

✔ 2. Créer des vues logiques sur des fichiers

Permet par exemple de joindre une directory table à une table contenant des métadonnées supplémentaires (ex : catalogues, tags, tables de contrôle).

✔ 3. Construire des pipelines de traitement de fichiers

Utilisable avec : Snowpark, External Functions
➡️ pour traiter les fichiers stockés (images, logs, PDF, etc.)

3. Activation d'une Directory Table

On peut l'activer :

  • À la création du stage → via CREATE STAGE
  • Après coup → via ALTER STAGE
“You can add a directory table to a stage when you create a stage or later using ALTER STAGE.”

✔ Exemple (documentation ThinkETL basée sur Snowflake)

Le paramètre DIRECTORY doit être activé :

CREATE OR REPLACE STAGE my_stage
    DIRECTORY = (ENABLE = TRUE);

✔ Activation sur stage existant :

ALTER STAGE my_stage SET DIRECTORY = (ENABLE = TRUE);

4. Comment interroger une Directory Table ?

La Directory Table devient disponible automatiquement sous forme d'un view‑like object associé au stage.

SELECT *
FROM DIRECTORY(@my_stage);

Cela retourne des colonnes comme :

  • RELATIVE_PATH
  • SIZE
  • LAST_MODIFIED
  • FILE_URL

5. Rafraîchir les Directory Tables

La directory table ne se met pas automatiquement à jour sauf si l'auto-refresh est activé (selon le cloud).

Sans auto‑refresh : ➡️ Il faut utiliser ALTER STAGE … REFRESH.

“You can refresh the directory table metadata manually using ALTER STAGE … REFRESH.”

✔ Coûts :

  • Le rafraîchissement automatique via notifications cloud → facturé comme Snowpipe (car Snowpipe gère les event notifications)
  • Le rafraîchissement manuel → facturé en Cloud Services "standard" (n'apparaît pas dans PIPE_USAGE_HISTORY)

6. Auto‑refresh (selon cloud provider)

Snowflake fournit des guides spécifiques selon le cloud (Azure Event Grid, AWS S3 notifications, GCP Pub/Sub).

Exemple Azure : L'auto‑refresh dépend d'événements blob : BlobCreated, BlobDeleted…

Points clés :
  • L'auto‑refresh permet d'ajouter/supprimer automatiquement les fichiers dans la directory table.
  • Certains événements (rename) ne déclenchent pas l'actualisation.

7. Facturation & Monitoring

“Overhead to manage event notifications … appears as Snowpipe charges.”

✔ Mesurer les coûts :

  • PIPE_USAGE_HISTORY (Snowpipe events)
  • AUTO_REFRESH_REGISTRATION_HISTORY (historique des fichiers et coûts associés)

8. Privileges nécessaires

Une directory table hérite des privilèges du stage. Elle n'a pas ses propres privilèges.

Via ThinkETL (confirmant la doc Snowflake) :

  • Pour interroger → READ ou USAGE selon stage interne/externe
  • Pour rafraîchir → WRITE / ALTER STAGE

9. Cas d'usage typiques (SnowPro Core)

✔ Inventaire des fichiers d'un data lake

Lister les nouveaux fichiers avant ingestion.

✔ Pipelines unstructured data (images, logs, PDF)

Utilisation avec Snowpark pour charger/processer chaque fichier.

✔ Contrôle de complétude / qualité d'ingestion

Comparer les fichiers attendus vs ceux réellement présents.

✔ Superviser l'évolution d'un répertoire cloud

Grâce aux métadonnées (last modified, taille…).
