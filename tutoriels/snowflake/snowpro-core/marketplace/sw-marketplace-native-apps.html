Snowflake Native Apps App Development

1. Qu'est‑ce qu'une Snowflake Native App ?

The Snowflake Native App Framework allows you to create data applications that leverage core Snowflake functionality and share them with other Snowflake accounts.

Les Snowflake Native Apps sont des applications exécutées directement dans le compte du consumer, permettant au provider :

  • d'embarquer logique applicative (Snowpark, SQL, JavaScript, Streamlit),
  • de partager données + business logic de façon sécurisée,
  • de distribuer et monétiser ces apps via Snowflake Marketplace ou via des listings privés.

✔ Objectifs du framework :

  • Permettre la création d'apps collaboratives sans déplacer les données.
  • Offrir un cadre de développement moderne (versionning, release channels, logs).
  • Exécuter l'app au plus près des données du client, répondant à des exigences fortes de sécurité.

2. Architecture : Provider vs Consumer

The framework is built around the provider and consumer model.

Provider

  • Crée une application package
  • Emballe des données, scripts, logique
  • Publie via listing (privé ou Marketplace)

Consumer

  • Installe l'app dans son propre compte
  • Configure les accès demandés
  • Exécute l'application et ses composants (SQL, Streamlit, UDF, SP…)

3. Application Package (côté Provider)

Providers create an application package that encapsulates data content, business logic, metadata, and setup script.

Un application package contient :

  • Données partagées
  • Logique applicative (SP, UDF, Snowpark…)
  • Streamlit UI (optionnel)
  • Manifest.yml (métadonnées)
  • Setup script SQL (exécuté à l'installation côté consumer)
  • Versions + patches (release channels)

Il s'agit d'un conteneur distribué ensuite via un listing.

4. Publier une Snowflake Native App (Provider)

You publish the app to consumers using listings. The application package becomes the data product of a listing.

✔ Workflow de publication :

  1. Créer et tester l'application package
    Ensure roles and privileges are set properly before publishing.
  2. Devenir Provider de listings
    Becoming a provider of listings… see Use listings as a provider.
  3. Définir les release directives (quelle version de l'app pour quels clients)
  4. Sécurité : lancer un automated security scan
    Initiate the automated security scan.
  5. Créer un listing
    • Peut être gratuit, privé, ou public
    • Peut inclure un plan tarifaire pour monétiser
      Optional: Add a pricing plan to get paid.
  6. Soumettre pour approbation (nécessaire pour le Marketplace public)
✔ Prérequis de rôle :
  • Le rôle publiant doit posséder l'application package
    The role must be the same role that created the application package.
  • CREATE LISTING privilège global
  • Pour l'auto-fulfillment : configuration par ORGADMIN

5. Ce qu'un Provider peut partager dans une Native App

The business logic of an application can include Streamlit app, stored procedures, functions (Snowpark, JavaScript, SQL).
Providers can also add shared data content to an app — schemas, tables, external or Iceberg tables, views.
✔ Restrictions importantes :
  • Pas de tables temporaires, volatiles ou transient.
    Shared tables cannot be temporary, volatile, or transient tables.
  • Pas de virtual columns / policies avec code Python/JS.
    Tables cannot have virtual columns; view definitions cannot contain Java/Python/JS.
  • Shared data non versionné : toutes versions de l'app utilisent les mêmes données.
    Shared data content is not versioned.

6. Installer et utiliser une Native App (Consumer)

Consumers can discover and install apps published to the Marketplace or via private listings.

✔ Workflow côté consumer :

  1. Installer l'app depuis un listing
    Install an app from a listing.
  2. Examiner les demandes d'accès
    • L'app peut demander : privilèges sur objets, références pour accéder à d'autres bases / objets
    Review access requests… including privileges and references required by the app.
  3. (Optionnel) Activer l'event table pour les logs
    Set up an event table to enable logging and event sharing.
  4. Utiliser l'app
    • via SQL Worksheets
    • via Streamlit UI
      Use the app… view Streamlit apps created by the provider.
  5. Gérer les privilèges sur l'objet application
    Le consumer peut accorder des droits aux autres utilisateurs.

7. Cas particulier : Trial Listings (Essai)

Apps installed from trial listings are suspended when the trial ends unless converted to a full listing.
Important pour examen :
  • Suspension automatique après période d'essai.
  • Les données internes à l'app sont conservées si l'app n'est pas supprimée.
  • S'il existe des objets créés hors de l'app : le consumer doit transférer ownership avant de désinstaller.

8. Atouts majeurs des Snowflake Native Apps (à citer pour l'examen)

  • Les apps s'exécutent dans le compte du consumer : zéro exposition de données.
  • Forte intégration avec Snowpark, Streamlit, SQL, collaboration.
  • Distribution via Listings (privés ou Marketplace).
  • Monétisation possible.
  • Gestion des versions via release channels.
  • Event logging & monitoring intégrés.
