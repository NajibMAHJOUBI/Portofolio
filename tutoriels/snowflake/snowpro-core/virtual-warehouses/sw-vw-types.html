Snowflake Virtual Warehouses

Les virtual warehouses sont les clusters de compute qui exécutent toutes les opérations nécessitant des ressources : requêtes SQL, DML, COPY INTO, etc.

Ils existent en deux types :

  • Standard (Gen1 ou Gen2)
  • Snowpark‑Optimized

1. Virtual Warehouse – Concepts clés

Un Warehouse fournit les ressources CPU, mémoire et stockage temporaire permettant :

  • d'exécuter des SELECT,
  • d'exécuter INSERT/UPDATE/DELETE,
  • de charger des données (COPY INTO table),
  • d'unloader (COPY INTO location).
Caractéristiques importantes :
  • peut être start/stop à volonté,
  • peut être redimensionné à chaud,
  • facturation à la seconde après un minimum de 60 secondes.

2. Standard Warehouses — Gen1 vs Gen2

Standard Warehouses (Gen1)

  • génération historique
  • tailles XS à 6X-Large
  • consommation doublée à chaque taille

Gen2 Standard Warehouses

Les Gen2 sont :

  • construits sur un matériel plus rapide,
  • optimisés pour DELETE/UPDATE/MERGE,
  • meilleurs pour les scans de tables.

Spécifications clés :

  • Choix via : GENERATION = '1' | '2' ou via RESOURCE_CONSTRAINT = STANDARD_GEN_1 / STANDARD_GEN_2.
  • Non disponible pour tailles X5LARGE et X6LARGE.
  • Gen2 devient progressivement la valeur par défaut dans plusieurs régions depuis 2025.
Note : Gen2 s'applique aux Warehouse standard, pas aux Snowpark‑optimized.

3. Snowpark‑Optimized Warehouses

Les Snowpark‑Optimized sont conçus pour des workloads :

  • à forte consommation mémoire,
  • nécessitant architectures CPU spécifiques,
  • ML training,
  • UDF/UDTF Snowpark.

Caractéristiques :

  • WAREHOUSE_TYPE = 'SNOWPARK-OPTIMIZED'
  • mémoire par nœud jusqu'à 16× plus élevée qu'un standard warehouse
  • options de resource constraints (MEMORY_1X, 16X, 64X…)

Exemple de création :

CREATE WAREHOUSE my_wh
WAREHOUSE_TYPE = 'SNOWPARK-OPTIMIZED';

4. Warehouse Sizes & Billing

Taille → quantité de compute par cluster

  • XS = 1 crédit/h
  • S = 2 crédits/h
  • … jusqu'à 6XL = 512 crédits/h

Facturation :

  • minimum 60 secondes
  • ensuite à la seconde
  • resizing = provisionnement immédiat → facturation proportionnelle

5. Multi‑Cluster Warehouses

Permettent de scaler horizontalement pour gérer la concurrence.

  • tailles de clusters fixées
  • nombre de clusters variable (ex : 1→3)

Utilisation :

  • amortir un pic de concurrence
  • éviter les requêtes en file d'attente

6. Bonnes Pratiques

Snowflake indique :

  • ne pas se focaliser uniquement sur la taille, car la facturation à la seconde rend les tailles plus grandes parfois plus économiques
  • expérimenter les tailles selon les workloads
  • s'applique aux single et multi‑cluster

Facteurs impactant la facture :

  • Taille du warehouse
  • Nombre de clusters
  • Temps d'exécution

7. Scaling Up vs Scaling Out

Source : Warehouse considerations — scaling section

Scaling Up (Vertical Scaling)

Changer la taille du warehouse → XS → S → M → L → …

Avantages :

  • plus de mémoire par cluster → réduit le remote spillage, donc accélère les queries
  • améliore performance des queries complexes (joins, aggregations)

Inconvénient : ne gère pas la concurrence (une seule file)

À utiliser quand :

  • les requêtes "spillent"
  • les opérations sont CPU/mémoire-intensives
  • le problème principal est la performance intrinsèque des requêtes

Scaling Out (Horizontal — Multi‑Cluster)

Augmenter le nombre de clusters du même warehouse (1 → n).

Avantages :

  • idéal pour gérer concurrence élevée
  • évite la mise en file d'attente

Inconvénients :

  • pas d'augmentation de RAM par requête
  • pas d'amélioration des performances individuelles

À utiliser quand :

  • de nombreuses requêtes simultanées
  • fonction BI à haut trafic
  • workloads multi-utilisateurs

Résumé

SituationSolution
Requêtes lentes, spillageScale Up
Beaucoup d'utilisateurs / concurrenceScale Out
Memory-bound workloadsScale Up
Pic de trafic BIScale Out

Points clés

  • Un warehouse doit être en marche pour exécuter DML/queries.
  • Facturation à la seconde après 60s.
  • Gen2 = meilleure performance + requêtes plus rapides.
  • Snowpark‑Optimized = recommandé pour ML / workloads lourds.
  • Scaling Up = puissance → performance. Scaling Out = clusters → concurrence.
  • Multi‑cluster uniquement en Enterprise Edition+.
  • Redimensionnement immédiat, sans arrêt du warehouse.
