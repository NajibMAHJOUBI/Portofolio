🧊 Multi‑Cluster Warehouses & Scaling Policies

Les entrepôts multi‑clusters (multi‑cluster warehouses) sont une fonctionnalité Enterprise Edition permettant d'augmenter la capacité de traitement horizontalement, en ajoutant dynamiquement des clusters pour gérer les pics de concurrence.

✅ 1. Qu'est‑ce qu'un Multi‑Cluster Warehouse ?

Sans multi‑cluster, un warehouse Snowflake est composé d'un seul cluster.

Quand plusieurs requêtes arrivent simultanément :

  • si suffisamment de ressources → exécution immédiate
  • sinon → requêtes mises en file d'attente

Avec les multi‑cluster warehouses, Snowflake peut provisionner plusieurs clusters pour absorber la concurrence, de façon statique ou dynamique.

Un multi‑cluster se définit par :

  • MIN_CLUSTER_COUNT
  • MAX_CLUSTER_COUNT
Les clusters supplémentaires fournissent une capacité parallèle supplémentaire, pas plus de mémoire par requête.

✅ 3. Modes de fonctionnement

✔ Maximized mode

Quand MIN = MAX, par exemple :

MIN_CLUSTER_COUNT = 4
MAX_CLUSTER_COUNT = 4
  • ➡ Snowflake démarre tous les clusters immédiatement et les maintient actifs tant que le warehouse tourne.
  • Avantage : capacité maximale constante.
  • Inconvénient : coût plus élevé.

✔ Auto‑Scale mode

Quand MIN < MAX, Snowflake ajuste automatiquement le nombre de clusters selon la charge.

  • Avantage : équilibre coût/performance.
  • Inconvénient : latence possible si un cluster doit être provisionné.

✅ 4. Scaling Policies (Standard vs Economy)

La section dédiée se trouve dans la documentation du multi‑cluster warehouse :

Les scaling policies déterminent comment Snowflake ajoute ou retire des clusters.

🔹 Standard Scaling Policy

Politique par défaut.

Comportement :

  • Démarre rapidement un nouveau cluster dès que des requêtes sont en file d'attente.
  • Arrête les clusters quand la charge reste faible.

Objectif : ➡ Réduire la latence, maintenir une haute réactivité.

Cas d'usage :

  • Dashboards BI
  • Workloads avec trafic instable
  • Nombreux utilisateurs concurrents

🔹 Economy Scaling Policy

Alternative plus orientée coût.

Comportement :

  • Les clusters ne démarrent que si Snowflake estime qu'un cluster supplémentaire sera pleinement utilisé.
  • Snowflake peut laisser des requêtes en file d'attente plus longtemps.

Objectif : ➡ Réduire la consommation de crédits.

Cas d'usage :

  • ETL batch
  • Workloads prévisibles
  • Jobs non interactifs

✅ 5. Comment Snowflake décide d'ajouter ou retirer des clusters ?

D'après la documentation :

Démarrage d'un cluster

Snowflake démarre un cluster supplémentaire lorsque :

  • les requêtes s'accumulent en file d'attente
  • les ressources manquent dans les clusters en cours

Arrêt d'un cluster

Snowflake arrête un cluster quand :

  • la charge baisse durablement
  • les requêtes du cluster sont terminées

Les décisions sont également influencées par la scaling policy (Standard ou Economy).

✅ 6. Fonctionnalités partagées avec les single‑cluster warehouses

Les multi‑cluster offrent les mêmes capacités qu'un warehouse classique :

  • Peut être redimensionné à chaud
  • Auto‑Suspend s'applique à l'ensemble du warehouse (pas cluster par cluster)
  • Auto‑Resume dès qu'une requête arrive

🎯 7. Points clés pour SnowPro Core

  • Multi‑cluster = solution Snowflake aux pics de concurrence, pas aux ralentissements de requêtes individuelles.
  • MIN = MAX → Maximized mode (tous les clusters actifs).
  • MIN < MAX → Auto‑scale mode.
  • Standard scaling → rapidité.
  • Economy scaling → économies.
  • Facturation = taille × nombre de clusters × durée.
  • Fonctionnalité Enterprise Edition.
