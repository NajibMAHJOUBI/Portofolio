1. Types of Roles dans Snowflake

Snowflake distingue trois catégories de rôles dans son modèle RBAC :

✔ 1.1. System‑defined roles

Ce sont les rôles intégrés, fournis par Snowflake.

✔ 1.2. Custom roles

Créés par les administrateurs selon les besoins métiers.

✔ 1.3. Database roles

  • Des rôles définis au niveau d'une database, qui ne peuvent pas être activés directement mais seulement assignés à des account roles.
  • Le contrôle d'accès dans Snowflake repose sur l'attribution des privilèges à des rôles et l'attribution des rôles aux utilisateurs.

2. System‑Defined Roles (Rôles systèmes)

Les rôles système sont fournis automatiquement et ne peuvent pas être supprimés.

✔ ORGADMIN

  • Rôle de gestion au niveau organisationnel (multi‑comptes).

✔ ACCOUNTADMIN

  • Rôle le plus puissant au niveau compte.
  • Combine les capacités de SYSADMIN + SECURITYADMIN.
  • Doit être utilisé seulement pour des tâches critiques (« break‑glass »).

✔ SECURITYADMIN

  • Gère les utilisateurs, les rôles, et les grants.
  • Peut accorder des privilèges aux autres rôles.

✔ USERADMIN

  • Crée et gère utilisateurs + rôles personnalisés.

✔ SYSADMIN

  • Gère les ressources techniques du compte :
    • création de warehouses, databases, schemas, tables…
    • Les rôles custom doivent généralement s'inscrire sous SYSADMIN.

✔ PUBLIC

  • Rôle attribué automatiquement à tous les utilisateurs.
  • Doit rester sans privilège critique.

Ces rôles définissent une structure hiérarchique recommandée par Snowflake.

3. Custom Roles (Rôles personnalisés)

Les rôles personnalisés permettent d'implémenter la sécurité selon les besoins de votre organisation.

✔ Points essentiels

  • Créés via CREATE ROLE.
  • Peuvent être attribués à :
    • des utilisateurs,
    • d'autres rôles (construction de hiérarchie),
    • des database roles.
  • Héritent des privilèges des rôles qu'ils contiennent.
  • Recommandé :
    • structurer les rôles par fonction (Data Engineer, BI Analyst, Data Scientist…),
    • éviter d'accorder des privilèges directement aux users (UBAC).

4. Role Hierarchy & Privilege Inheritance

Snowflake permet de créer une hiérarchie de rôles en attribuant des rôles à d'autres rôles.

✔ Héritage des privilèges

  • Si ROLE_A est accordé à ROLE_B : ROLE_B hérite de tous les privilèges de ROLE_A.
  • Cette hiérarchie peut être profonde et multi‑niveaux.
OWNERSHIP n'est pas héritable
  • Le privilège OWNERSHIP est unique et représente la pleine propriété d'un objet.
  • Il ne peut pas être partagé ni propagé dans la hiérarchie.

5. Primary Role & Secondary Roles

Lorsqu'un utilisateur se connecte, il active un rôle principal (primary role).

Les secondary roles peuvent être activés pour étendre temporairement les privilèges disponibles.

✔ 5.1. Primary Role

  • Le rôle actif par défaut dans la session.
  • Tous les objets créés dans la session sont propriétés du primary role.

✔ 5.2. Secondary Roles

  • Permettent d'ajouter temporairement des privilèges supplémentaires dans une session.
  • S'activent par : USE SECONDARY ROLES ALL;
  • Permettent l'usage exceptionnel de UBAC (grants directs aux utilisateurs).
✔ 5.3. Importance dans Snowflake

Les administrateurs doivent savoir quel rôle est actif car il définit :

  • l'accès aux objets,
  • l'owner des objets créés,
  • les privilèges disponibles pendant la session.
