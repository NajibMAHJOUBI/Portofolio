Snowflake - IdP et SSO Workflows

Niveau Intermédiaire
Mis à jour: Février 2026 Durée: 15 min Difficulté: Intermédiaire
Snowflake SSO Sécurité

✅ 1. Supported Identity Providers (IdP)

Source :

Snowflake fonctionne comme Service Provider (SP) et délègue l'authentification à un Identity Provider (IdP) compatible SAML2.

✔ 1.1. IdP avec support natif Snowflake

Les fournisseurs suivants disposent d'une intégration native avec Snowflake, simplifiant la configuration SSO :

  • Okta (cloud)
  • Microsoft Entra ID (ancien Azure Active Directory)

✔ 1.2. IdP SAML 2.0 compatibles (configuration personnalisée nécessaire)

Snowflake supporte (via SAML2) la majorité des fournisseurs identitaires du marché :

  • Google G Suite
  • OneLogin
  • Ping Identity
  • PingOne
  • Tout autre IdP SAML 2.0‑compliant

👉 Pour ceux-ci, il faut créer une application personnalisée Snowflake dans l'IdP.

✔ 1.3. Multi‑Identity Providers (Multi‑IdP)

Snowflake permet d'enregistrer plusieurs IdP simultanément, afin que différents utilisateurs puissent s'authentifier via différents IdP.

Limitation importante : Seuls certains drivers supportent Multi‑IdP :
  • JDBC
  • ODBC
  • Python

✅ 2. Supported SSO Workflows (Workflows d'authentification SSO supportés)

Source :

Snowflake prend en charge plusieurs flux d'authentification SSO basés sur SAML2. Ceux-ci couvrent login, logout et expirations de session.

✔ 2.1. Login workflows

🔹 Snowflake‑Initiated Login

  1. L'utilisateur accède à Snowflake (ex : https://.snowflakecomputing.com).
  2. Snowflake redirige l'utilisateur vers l'IdP pour authentification.
  3. L'IdP renvoie une assertion SAML valide → ouverture de session Snowflake.

💡 Une configuration permet de rediriger automatiquement l'utilisateur vers l'IdP sans afficher la page de login Snowflake.

🔹 IdP‑Initiated Login

  1. L'utilisateur ouvre son portail IdP (Okta, Entra ID…).
  2. Clique sur l'application Snowflake.
  3. L'IdP envoie directement une assertion SAML à Snowflake → session ouverte.

✔ 2.2. Logout workflows

Snowflake supporte le logout initié par Snowflake ou par l'IdP.

Le comportement final dépend de l'origine du logout.

Ex. : Un logout effectué dans Snowflake peut ne pas déconnecter l'utilisateur de l'IdP (selon les capacités de celui‑ci).

✔ 2.3. Session timeout workflows

Lorsqu'une session Snowflake expire pour inactivité, les actions dépendent encore une fois :

  • de qui initie la fin de session (Snowflake ou IdP),
  • et de la manière dont l'IdP gère les sessions persistantes.

🎯 Points clés SnowPro Core à retenir

🔐 Identity Providers

  • Snowflake = Service Provider
  • Support natif : Okta, Microsoft Entra ID
  • Autres IdP SAML2 possibles via configuration custom
  • Multi‑IdP supporté (limité à JDBC/ODBC/Python)

🔐 SSO Workflows

  • Deux types de login :
    • Snowflake‑initiated
    • IdP‑initiated
  • Logout et timeout sont supportés mais leur comportement dépend de l'initiateur

🔐 Importance pour l'examen

  • Comprendre que Snowflake ne gère pas les mots de passe IdP
  • Comprendre le mécanisme SAML2 et rôle SP/IdP
  • Savoir reconnaître les workflows SSO supportés
