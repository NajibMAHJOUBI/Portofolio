Logging & Tracing – Synthèse SnowPro Core

La fonctionnalité Logging & Tracing fait partie des capacités d'observabilité de Snowflake. Elle permet d'enregistrer, analyser et corréler les événements générés par vos applications Snowpark, UDF, Stored Procedures, et autres workloads exécutés dans Snowflake.

1. Objectif du Logging & Tracing dans Snowflake

Snowflake offre un mécanisme pour :

  • Enregistrer des logs applicatifs depuis Snowpark (Python, Java, Scala) ou des procédures stockées.
  • Tracer les événements d'exécution afin de diagnostiquer les erreurs, mesurer les performances et auditer l'activité applicative.
  • Centraliser les logs dans des event tables que vous pouvez interroger en SQL.
  • Faciliter le debug, le monitoring et la conformité (auditabilité).

2. Models de Logging supportés

✔ Application Logging

Utilisé pour enregistrer :

  • Messages de debug
  • Informations métier
  • Erreurs applicatives
  • Données contextuelles (identifiants, étapes…)

Les logs sont envoyés via l'API Snowpark Logging et stockés dans une Event Table.

✔ Tracing

Utilisé pour suivre :

  • Les étapes d'exécution d'un pipeline
  • Les appels imbriqués (UDF → SP → Snowpark)
  • Les durées d'exécution
  • Les dépendances internes

Le tracing permet une analyse en profondeur, similaire aux solutions de tracing distribué.

3. Les Event Tables

Les event tables sont des objets Snowflake spécialement conçus pour stocker les logs :

  • Stockage optimisé pour requêtage SQL
  • Queryable via SELECT standard
  • Peut être intégrée dans un pipeline (e.g. Snowpipe, tasks)
  • Peut être utilisée pour dashboarding (Streamlit, BI, Observabilité)

Une event table contient généralement :

ColonneDescription
TIMESTAMPmoment exact du log
LEVELDEBUG / INFO / WARN / ERROR
MESSAGEmessage enregistré
CONTEXTdonnées additionnelles JSON
TRACE_IDidentifiant permettant la corrélation
SPAN_IDsous‑événement spécifique

4. Logging & Tracing avec Snowpark

✔ Snowpark Python / Java / Scala

Les bibliothèques Snowpark intègrent un module logging compatible Snowflake.

Possible de :

  • Créer un logger
  • Écrire des messages dans l'event table
  • Attacher des métadonnées (context & tags)

Exemples d'utilisations typiques :

  • Audit de pipeline
  • Monitoring ML
  • Debugging UDF / SP
  • Enregistrement des erreurs gérées & non gérées

5. Logging dans les Stored Procedures (SP)

Les stored procedures peuvent utiliser :

  • snowflake.snowpark.logging (Java/Python SP)
  • la fonction système SYSTEM$LOG() (JavaScript SP)

Les logs sont envoyés vers une event table ou vers le procedure tracing.

6. Tracing : corrélation des événements

Le tracing permet de reconstruire le chemin d'exécution complet d'un workflow :

  • Chaque opération génère un trace ID
  • Chaque sous‑opération génère un span ID
  • Les dépendances sont reliées automatiquement

Cela permet :

  • d'identifier un bottleneck,
  • de comprendre une erreur,
  • d'optimiser un pipeline Snowpark/SQL/UDF.

8. Patterns classiques à connaître

  • Logging depuis une UDF/UDTF → event table
  • Tracing d'un pipeline Snowpark → trace ID + span ID
  • Corrélation cross‑language (Python → SQL → SP JS → Snowpark)
  • Analyse via : SELECT * FROM my_event_table WHERE LEVEL = 'ERROR';

9. Synthèse

  • Snowflake prend en charge Logging & Tracing natif pour Snowpark, SP, UDF/UDTF.
  • Les logs et traces sont stockés dans des event tables.
  • L'architecture Logging/Tracing permet audit, debugging, monitoring.
  • Le tracing utilise trace IDs et span IDs pour corrélation.
  • Compatible avec Snowpark Python/Java/Scala et SP JavaScript/Python/Java.
  • Peut être interrogé en SQL comme n'importe quelle table Snowflake.
