1. Access Control Framework

Snowflake utilise un modèle hybride de contrôle d'accès, combinant :

✔ RBAC – Role-Based Access Control (modèle principal)

  • Les privilèges sont attribués à des rôles, pas à des utilisateurs.
  • Les utilisateurs se voient ensuite attribuer un ou plusieurs rôles.
  • C'est le modèle recommandé car il est scalable et maintenable.

✔ DAC – Discretionary Access Control

  • Chaque objet Snowflake a un OWNER (un rôle).
  • L'owner d'un objet peut accorder, révoquer des privilèges, et transférer l'OWNERSHIP.

✔ UBAC – User-Based Access Control (secondaire)

  • Snowflake permet d'accorder des privilèges directement à un utilisateur.
  • Ces privilèges ne sont pris en compte que si USE SECONDARY ROLES = ALL.
  • Ce mécanisme doit rester exceptionnel.

✔ Concepts fondamentaux :

Élément Définition
User Identité Snowflake (humain ou service).
Role Conteneur de privilèges. Peut être attribué à un utilisateur ou à un autre rôle.
Privilege Droit d'exécuter une action sur un objet.
Securable Object Objet auquel un privilège peut être accordé.

2. Securable Objects (Objets Sécurisables)

Tous les objets sécurisables sont organisés dans une hiérarchie logique :

Organization → Account → Database → Schema → Object

✔ Types d'objets sécurisables

Exemples :

  • Database
  • Schema
  • Table, View, Stream, Stage
  • Warehouse
  • File Format, Sequence
  • Functions / Procedures
Règle essentielle pour l'accès

Pour accéder à un objet, il faut :

  • USAGE sur la Database
  • USAGE sur le Schema
  • Le privilège spécifique (ex : SELECT, INSERT, etc.)

3. Role Hierarchy & Privilege Inheritance

Dans Snowflake, les rôles peuvent être imbriqués :

✔ Héritage

  • Un rôle A peut être attribué à un rôle B.
  • B hérite automatiquement de tous les privilèges de A.
  • Cette hiérarchie permet une gestion flexible et granulaire.

✔ Rôle principal vs rôles secondaires

  • Un utilisateur active un primary role dans sa session.
  • Les privilèges basés sur UBAC ne sont actifs que si les secondary roles sont activés avec : USE SECONDARY ROLES ALL;
OWNERSHIP et héritage
  • Le privilège OWNERSHIP n'est pas héritable et ne peut pas être partagé.
  • OWNERSHIP = privilège absolu → transférable seulement via GRANT OWNERSHIP.

4. Privileges (Privilèges d'Accès)

Un privilège est une autorisation permettant d'effectuer une action spécifique sur un objet.

✔ Catégories de privilèges

Privilèges sur Database

  • USAGE
  • CREATE SCHEMA
  • IMPORTED PRIVILEGES

Privilèges sur Schema

  • USAGE
  • CREATE TABLE / CREATE VIEW / CREATE STAGE / …
  • MODIFY

Privilèges sur Tables / Views

  • SELECT
  • INSERT, UPDATE, DELETE
  • TRUNCATE
  • REFERENCES

Privilèges sur Warehouses

  • USAGE
  • OPERATE
  • MONITOR
  • MODIFY
Privilèges supérieurs
  • OWNERSHIP : donne contrôle total sur l'objet.
  • Permet de transférer l'ownership.
  • Implique automatiquement TOUS les autres privilèges.

✔ Grants & Revokes

Exemples usuels :

GRANT SELECT ON TABLE mydb.sales TO ROLE analyst;
GRANT USAGE ON DATABASE mydb TO ROLE analyst;
REVOKE SELECT ON TABLE mydb.sales FROM ROLE analyst;

5. Synthèse

✔ RBAC = modèle recommandé

  • On crée des rôles
  • On accorde des privilèges à ces rôles
  • On assigne les rôles aux utilisateurs

✔ OWNERSHIP

  • Privilège suprême (non héritable)
  • Un seul owner par objet

✔ Hiérarchie d'accès

  • USAGE sur DB → USAGE sur Schema → privilège sur l'objet

✔ Héritage des rôles

  • Les rôles peuvent être imbriqués
  • Les privilèges se propagent dans la hiérarchie

✔ UBAC = exceptionnel

  • Ne fonctionne que si les secondary roles sont activés
