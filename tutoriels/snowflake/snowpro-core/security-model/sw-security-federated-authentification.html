1. Définition : Qu'est‑ce qu'un environnement fédéré ?

Source :

Un environnement d'authentification fédérée sépare :

  • L'authentification (faite par un fournisseur externe, l'IdP)
  • L'accès au service (Snowflake), via SSO

L'IdP authentifie l'utilisateur. Snowflake reçoit la preuve d'authentification et ouvre la session → SSO.

✔ Composants d'un environnement fédéré :

Composant Rôle
SP (Service Provider) Snowflake agit en tant que Service Provider.
IdP (Identity Provider) Authentifie l'utilisateur, maintient les credentials. Fournit les assertions SAML à Snowflake.

2. Identity Providers supportés

Source :

✔ Support natif Snowflake :

  • Okta
  • Microsoft Entra ID (anciennement Azure AD)

✔ Autres IdP SAML 2.0 compatibles :

  • Google G Suite
  • OneLogin
  • Ping Identity / PingOne

Pour les IdP non natifs, il faut créer une custom SAML application dans l'IdP.

3. Utilisation de plusieurs IdP

Source :

Snowflake peut être configuré pour utiliser plusieurs IdP simultanément.

Limitation : seuls certains drivers supportent multi‑IdP (JDBC, ODBC, Python).

4. Workflows SSO supportés

Source :

Snowflake supporte les workflows suivants :

✔ SSO Login

  • Snowflake‑initiated login
    L'utilisateur se connecte depuis la page Snowflake
    Peut être configuré pour être redirigé automatiquement vers l'IdP (sans afficher la page Snowflake)
  • IdP‑initiated login
    L'utilisateur se connecte dans l'IdP
    Sélectionne l'application Snowflake
    L'IdP envoie une assertion SAML à Snowflake

✔ SSO Logout

Prise en charge du logout initié par Snowflake ou IdP. Le comportement dépend de l'initiateur (Snowflake ou IdP)

✔ Timeout (session inactivité)

Fonctionne en conformité avec la session côté Snowflake et IdP

5. Configuration technique (vue d'ensemble)

(Les détails complets sont dans la page Configuring Snowflake for Federated Auth, mais les concepts viennent de l'Overview.)

✔ Utilisation d'une SAML2 Security Integration

  • Nécessaire pour connecter Snowflake à l'IdP
  • À remplacer l'ancien paramètre : SAML_IDENTITY_PROVIDER (migration recommandée)

✔ Points importants lors de la configuration :

  • Le Snowflake ACS URL doit correspondre exactement au format attendu par l'IdP
  • Certificats SAML / metadata doivent être fournis
  • Snowflake peut signer les requêtes SAML et chiffrer les assertions SAML

6. Gestion des utilisateurs avec fédération

Source :

Même en mode fédéré :

  • Snowflake permet encore de conserver des mots de passe Snowflake pour des utilisateurs humains.
    ➜ Mais Snowflake ne le recommande pas.
  • Pour rendre un utilisateur strictement fédéré, il faut retirer son mot de passe Snowflake (ALTER USER).
  • L'administrateur doit cependant impérativement garder au moins un compte admin avec mot de passe Snowflake pour résoudre les problèmes d'IdP.
Limitation : Le flag MUST_CHANGE_PASSWORD ne s'applique pas quand la fédération est active.

7. Désactivation / suppression d'utilisateurs fédérés

Source :

Si un utilisateur est supprimé ou désactivé dans Snowflake :

  • Il peut toujours se connecter à son IdP
  • Mais Snowflake refuse la session
  • Il doit être recréé ou réactivé dans Snowflake pour restaurer l'accès

8. Points clés SnowPro Core – à mémoriser absolument

✔ Concepts fondamentaux

  • Snowflake = Service Provider (SP)
  • IdP authentifie = fournit SAML assertion à Snowflake

✔ IdP supportés

  • Okta & Entra ID (support natif)
  • Tous IdP SAML 2.0 (via custom app)

✔ Modes de login

  • Snowflake‑initiated
  • IdP‑initiated
  • Redirection automatique possible

✔ Multi‑IdP

  • Supporté (limité par les drivers)

✔ Recommandation sécurité

  • Éviter les mots de passe Snowflake pour les utilisateurs humains
  • Mais garder au moins un admin local pour l'urgence

✔ SAML2 Security Integration

  • Objet indispensable à tout SSO
  • Gère certificat, metadata, URLs

9. Synthèse

Snowflake utilise un modèle SSO fédéré basé sur SAML2 : un IdP authentifie l'utilisateur, Snowflake l'accepte en tant que SP. Snowflake‑initiated ou IdP‑initiated login sont tous deux supportés. Okta & Entra ID ont un support natif. Le SSO est configuré via une SAML2 Security Integration et Snowflake recommande de ne plus stocker de mots de passe pour les utilisateurs humains — sauf un compte admin d'urgence.
