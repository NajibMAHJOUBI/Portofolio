1. Principes fondamentaux du clonage

Le clonage Snowflake (aussi appelé Zero‑Copy Cloning) est une fonctionnalité permettant de créer une copie instantanée d'un objet (table, schéma, base, etc.) sans dupliquer physiquement les données. Snowflake référence simplement les mêmes micro‑partitions au moment du clonage.

Zero‑Copy

Le clonage ne duplique pas les données :

  • Les micro‑partitions sont partagées entre source et clone.
  • Le clone n'ajoute du stockage que si des modifications ultérieures sont apportées (copy‑on‑write). [docs.snowflake.com]

Objets pouvant être clonés

Snowflake permet de cloner :

  • Bases de données
  • Schémas
  • Tables
  • Dynamic tables
  • Event tables
  • Iceberg tables
  • Stages externes, file formats, sequences, tasks, streams [docs.snowflake.com]

2. Syntaxe de base du clonage

Exemple général

CREATE OR REPLACE   CLONE ;

Clonage avec Time Travel

Le clonage peut cibler un instant passé :

CREATE TABLE my_clone CLONE my_table
    AT (TIMESTAMP => '2024-01-01 10:00:00');

Paramètres possibles :

  • TIMESTAMP => <timestamp>
  • OFFSET => <time_difference>
  • STATEMENT => <query_id> [docs.snowflake.com]

3. Clonage et Time Travel : points importants

Lors du clonage d'objets avec AT | BEFORE, Snowflake recrée l'objet tel qu'il était :

  • à un moment précis,
  • après une durée relative,
  • après une requête spécifique (STATEMENT). [docs.snowflake.com]

xceptions :

Certaines tables peuvent être ignorées si :

  • elles ont été purgées de Time Travel, → utiliser IGNORE TABLES WITH INSUFFICIENT DATA RETENTION [docs.snowflake.com]

4. Clonage des privilèges & COPY GRANTS

Par défaut :

  • Les privilèges ne sont pas clonés pour la plupart des objets.
  • Il faut les redonner manuellement.

Exception :

→ Les commandes prenant en charge COPY GRANTS (ex: CREATE TABLE … CLONE) peuvent cloner tous les privilèges sauf OWNERSHIP. [docs.snowflake.com]

Exemple

CREATE TABLE table_clone CLONE table_src COPY GRANTS;

5. Clonage d'objets complexes : points spécifiques

A. Clonage de bases ou schémas

  • Le clone hérite des privilèges des objets contenus, mais pas des privilèges du conteneur lui-même (BD/schéma). [docs.snowflake.com]

B. Clonage des Managed Access Schemas

  • Les exigences en privilèges varient selon que le schéma source est géré ou non. [docs.snowflake.com]

C. Clonage et paramètres des objets

  • Les paramètres d'objet sont hérités lors du clonage (si définis sur l'objet). [docs.snowflake.com]

D. Clonage et séquences

Pour les séquences utilisées dans les valeurs par défaut :

  • si table + séquence sont clonées ensemble → la table clonée utilise la séquence clonée,
  • sinon elle continue d'utiliser la séquence source. [docs.snowflake.com]

6. Considérations liées aux DDL/DML, Time Travel & Retention

Certaines opérations récentes sur l'objet source peuvent influencer le clone :

  • DDL et DML non encore finalisés,
  • rétention Time Travel (important pour les clones historiques),
  • tables transientes (retenue faible → risque de tables ignorées). [docs.snowflake.com]

7. Avantages pratiques du clonage Snowflake

Environnements de dev/QA rapides

Créer des environnements DEV et QA à partir de PROD en quelques secondes, sans consommation de stockage initiale.

Reproduire un état historique

Grâce à Time Travel, on peut cloner un objet tel qu'il était à un moment donné (pratique pour audits et analyses).

Expérimentations sans risque

Tester des transformations ou des redesigns sans affecter les données sources.

8. Limitations à retenir pour l'examen

Clonage impossible pour :

Tables temporaires (ne supportent pas Time Travel) [docs.snowflake.com]

Ownership jamais copié

Toujours redonner explicitement OWNERSHIP.

Rétention Time Travel peut exclure des tables

→ utiliser IGNORE TABLES WITH INSUFFICIENT DATA RETENTION. [docs.snowflake.com]
