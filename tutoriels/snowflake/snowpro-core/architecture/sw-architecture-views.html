1. Définition d'une View

Une view est un objet Snowflake qui expose le résultat d'une requête SQL comme s'il s'agissait d'une table.

La définition de la vue est fournie via la commande CREATE VIEW.

Objectifs des vues :

  • Combiner des données
  • Séparer des données selon les besoins utilisateurs
  • Protéger des données sensibles (ex. masquage via une vue partielle)

Exemple d'usage : créer un jeu de vues différentes pour des rôles internes (ex. médecins vs comptables).

2. Fonctionnement général

Les vues peuvent être utilisées comme des tables

Elles sont utilisables dans :

  • des JOIN
  • des sous‑requêtes
  • des requêtes analytiques

Noms qualifiés

Une vue peut référencer une table via :

  • nom totalement qualifié : db.schema.table
  • partiellement qualifié : schema.table
  • non qualifié : table
    Si le schéma n'est pas précisé, Snowflake cherche la table dans le même schéma que la vue, pas dans le schéma actif.

3. Types de Vues dans Snowflake

Snowflake distingue deux types principaux :

1 - Non‑Materialized Views (vues classiques)

  • Basées sur une définition de requête réévaluée à chaque exécution.
  • Peuvent être lentes si la requête est lourde.
  • N'occupent presque pas de stockage (seule la définition SQL est stockée).

2 - Materialized Views

  • Stockent les résultats matérialisés.
  • Nécessitent du stockage Snowflake.
  • Accélèrent les requêtes répétitives.

4. Création d'une Vue

Commande CREATE VIEW

Exemples tirés de la documentation : 

CREATE VIEW doctor_view AS
SELECT patient_id, patient_name, diagnosis, treatment
FROM hospital_table;

CREATE VIEW accountant_view AS
SELECT patient_id, patient_name, billing_address, cost
FROM hospital_table;

Ces vues permettent de segmenter l'information selon les rôles des utilisateurs.

5. Usages typiques des Vues

A. Ségrégation des données

Exposer des colonnes différentes pour différentes catégories d'utilisateurs.

B. Abstraction

Présenter une interface stable même si les tables sous-jacentes changent.

C. Sécurité

Restreindre l'accès aux données sensibles via une vue filtrée.

D. Simplification

Permet de masquer des jointures ou de la logique complexe.

6. Syntaxe & Bonnes pratiques

Nommer clairement les vues

  • Exemple : vw_sales, vw_customer_public.

Éviter les vues profondément imbriquées

  • Pour des raisons de performance (chaînes de dépendances longues).

Utiliser des noms qualifiés dans CREATE VIEW

  • Évite les comportements imprévisibles si l'utilisateur change de schéma actif.

Attention aux évolutions des tables sous-jacentes

  • Une modification de table peut casser une vue si des colonnes disparaissent.
  • Une bonne pratique est de garder à l'esprit l'importance du nommage explicite dans CREATE VIEW.
