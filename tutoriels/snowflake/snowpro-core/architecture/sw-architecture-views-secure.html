1. Définition & Objectif des Secure Views

Une Secure View est une vue Snowflake dont la définition et les optimisations internes sont restreintes afin d'éviter toute fuite d'information. Snowflake garantit ainsi :

  • Que les utilisateurs ne peuvent pas accéder aux données sous-jacentes autrement que via la vue, même indirectement.
  • Que la définition de la vue (le texte SQL) n'est visible que par les rôles autorisés.

Pourquoi des Secure Views ?

Les vues non sécurisées peuvent exposer des données en raison :

  • d'optimisations internes nécessitant l'accès aux tables sources,
  • d'erreurs générées par du code utilisateur permettant d'inférer l'existence de données sensibles (ex : division par zéro dans une logique conditionnelle).

Les Secure Views désactivent ces optimisations pour empêcher ces fuites.

2. Risques liés aux vues non sécurisées

Snowflake illustre le risque par un exemple :

SELECT *
FROM widgets_view
WHERE 1/iff(color = 'Purple', 0, 1) = 1;

Si la couleur "Purple" existe en base, la division par zéro déclenche une erreur → l'utilisateur infère l'existence d'une donnée à laquelle il n'a pas accès.

Les Secure Views évitent ce scénario.

3. Quand utiliser une Secure View ?

Utilisation recommandée lorsque :

  • on expose des données sensibles,
  • on souhaite empêcher la révélation de la logique interne ou des structures sous-jacentes,
  • les vues sont utilisées dans des contextes de data sharing entre comptes Snowflake,
  • les vues servent de barrière de sécurité, et non simplement de simplification de requêtes.

Attention :

  • Les Secure Views peuvent être moins performantes que les vues classiques.
  • Il faut arbitrer entre confidentialité et performance.

4. Syntaxe & Création d'une Secure View

Créer une Secure View

CREATE OR REPLACE SECURE VIEW my_secure_view AS
SELECT col1, col2
FROM sensitive_table;

Convertir une vue existante

ALTER VIEW my_view SET SECURE;

Revenir à une vue non sécurisée

ALTER VIEW my_view UNSET SECURE;

5. Visibilité & Confidentialité

Dans une Secure View :

  • la définition de la vue n'est visible que par le rôle propriétaire,
  • les autres utilisateurs ne peuvent pas l'obtenir via DESC VIEW, SHOW VIEWS, ni d'autres interfaces,
  • certaines erreurs sont redactées (cachées) pour empêcher des inférences sur la structure ou le contenu.

6. Secure Views et Data Sharing

Les Secure Views sont fortement recommandées lors du Secure Data Sharing entre comptes Snowflake :

  • elles évitent d'exposer la structure interne des tables,
  • elles permettent de partager uniquement l'information autorisée tout en protégeant le reste.

Exemples :

  • partager des données structurées via une Secure View
  • partager des fichiers non structurés via une Secure View qui répond par des scoped URLs ou pre-signed URLs

7. Performance

Points clés :

  • Les Secure Views désactivent certaines optimisations internes pour éviter des fuites → performances parfois plus faibles.
  • À n'utiliser que lorsque la confidentialité prime.

Lorsque les Secure Views sont utilisées pour des tables très volumineuses partagées :

  • recommander l'utilisation de clustering keys sur les tables sous-jacentes pour améliorer les performances côté consommateur.
