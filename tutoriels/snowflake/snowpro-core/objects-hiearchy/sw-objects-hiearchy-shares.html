Data Sharing (Provider)

Snowflake permet de partager des données sans les copier, de manière sécurisée et gouvernée. En tant que provider, vous créez des shares et les rendez accessibles à des comptes consommateurs.

1. Qu'est‑ce qu'un Provider Snowflake ?

Un provider est un compte Snowflake qui décide de partager une partie de ses données avec d'autres comptes (consumers).

Snowflake précise que la fonctionnalité provider sharing n'est pas active pour tous les comptes, selon édition/paramétrage.
→ Si non activée, contacter Snowflake Support. [docs.snowflake.com]

2. Le concept de SHARE (objet de partage)

Un share est un objet Snowflake contenant les objets et privilèges que vous rendez accessibles.

Un share peut contenir :

  • plusieurs objets d'un même database,
  • ou des objets provenant de différents databases. [docs.snowflake.com]

Une fois un consumer ajouté :

➡️ le share devient immédiatement accessible.

Important :
  • Les lignes nouvellement modifiées ou ajoutées deviennent immédiatement visibles.
  • Un objet recréé (DROP + CREATE) n'est pas automatiquement resharé même s'il porte le même nom. [docs.snowflake.com]

3. Types de partage : direct share, listings, cross‑cloud

Selon la documentation :

✔ Partage direct (Secure Data Sharing)

  • Partage dans la même région
  • Lecture seule
  • Zero‑copy
  • Simple et rapide [docs.snowflake.com]

✔ Partage multi‑cloud / multi‑région

Vous pouvez partager des données à travers différentes régions et plateformes cloud, en laissant Snowflake gérer la réplication si nécessaire. [docs.snowflake.com]

✔ Snowflake Marketplace & Listings

Permet d'offrir des datasets publiquement ou à des comptes cibles avec plus de métadonnées (titre, description, exemples). [docs.snowflake.com]

4. Processus pour créer un share (Provider)

Étapes décrites par Snowflake : [docs.snowflake.com]

1. Créer un share

CREATE SHARE my_share;

2. Ajouter des privilèges sur les objets

Deux approches possibles :

  • via database roles
  • ou via GRANT ... TO SHARE

Exemple :

GRANT USAGE ON DATABASE mydb TO SHARE my_share;
GRANT SELECT ON ALL TABLES IN SCHEMA mydb.public TO SHARE my_share;

3. Ajouter un consumer

ALTER SHARE my_share ADD ACCOUNTS = ('ORG.ACCOUNT_NAME');

4. Maintenance

  • Ajouter/enlever objets
  • Ajouter/enlever comptes
  • Rafraîchir autorisations si objets recréés

5. Points de conformité et sécurité

Snowflake indique :

Snowflake n'est pas responsable de la conformité HIPAA/HITRUST entre comptes.
C'est au provider de vérifier qu'un Business Critical ne partage pas des données sensibles avec non‑Business Critical. [docs.snowflake.com]

Recommandations Snowflake pour comptes Business Critical :

  • Ne pas partager de données sensibles avec des comptes non‑BC
  • Créer un second compte non-BC pour données moins sensibles
  • Attention à Tri‑Secret Secure → accès KMS peut être déclenché via le partage [docs.snowflake.com]

6. Particularités fonctionnelles à connaître (Exam)

  • Un share est lecture seule — Les consumers ne peuvent pas modifier les données.
  • Zero‑copy sharing — Pas de duplication de données → coûts de stockage uniquement chez le provider.
  • Les modifications sont immédiatement visibles → Les consumers voient l'évolution en temps réel. [docs.snowflake.com]
  • Les objets recréés doivent être ré‑autorisés dans le share — Important dans les questions pièges de l'examen. [docs.snowflake.com]
  • On peut partager des données de plusieurs databases dans un même share [docs.snowflake.com]
  • Partage cross‑région / cross‑cloud supporté [docs.snowflake.com]

7. Ce que le consumer voit

Un consumer crée une database locale "virtuelle" :

CREATE DATABASE my_consumed_db FROM SHARE provider_org.provider_account.my_share;

Une fois créée :

  • Il peut requêter les données
  • Aucun stockage n'est consommé dans son compte (sauf cache)
  • Il paie uniquement son compute
