Stored Procedures Overview

Les Stored Procedures permettent d'exécuter du code procédural dans Snowflake. Elles sont essentielles pour automatiser des opérations répétitives et encapsuler de la logique métier ou administrative trop complexe pour de simples requêtes SQL.

1. Définition d'une Stored Procedure

Une stored procedure est un objet Snowflake contenant du code procédural qui peut :

  • exécuter des instructions SQL,
  • utiliser des structures de contrôle (boucles, conditions…),
  • organiser plusieurs opérations en un seul appel,
  • être réutilisée par différents utilisateurs ou processus.

[docs.snowflake.com]

Snowflake précise qu'une procédure est utile pour automatiser des tâches nécessitant plusieurs opérations SQL, comme un nettoyage de tables. [docs.snowflake.com]

2. Cas d'usage typiques

Selon la documentation : [docs.snowflake.com]

  • ✔ Automatiser des tâches répétées (purge, maintenance, traitement de lots)
  • ✔ Générer et exécuter du SQL dynamique
  • ✔ Cacher des opérations complexes derrière un appel simple
  • ✔ Donner accès à des fonctions sensibles grâce au modèle "owner's rights" (voir ci‑dessous)

Exemple donné dans la doc : un nettoyage de tables basé sur une date passée en paramètre. [docs.snowflake.com]

3. "Owner's Rights" : exécution avec les privilèges du propriétaire

Particularité clé :

Une stored procedure s'exécute avec les privilèges du rôle qui la possède, pas du rôle qui la lance.

[docs.snowflake.com]

  • Cela permet de déléguer des tâches sensibles (ex. DELETE, DDL) à des utilisateurs qui n'ont pas ces privilèges directement.
  • ⚠ Il existe cependant des limitations aux owner's rights (documentées dans les sections annexes Snowflake).

4. Stored Procedure vs UDF : différences essentielles

La documentation insiste sur les différences : [docs.snowflake.com]

Stored Procedure UDF
Peut exécuter plusieurs SQL statements Doit retourner un résultat direct
Peut effectuer du DDL/DML, gérer des transactions Ne peut pas exécuter de DDL/DML
Peut retourner une valeur ou rien Doit toujours renvoyer 1 valeur (ou un tableau via UDTF)
Utilise CALL Utilisée dans une expression SQL
Stocker cette distinction est indispensable pour SnowPro Core.

5. Langages supportés

Vous écrivez la logique (handler) dans l'un des langages suivants : [docs.snowflake.com]

LangageSupport
JavaOui
JavaScriptOui
PythonOui
ScalaOui
SQL ScriptingOui (bloc SQL procédural)

Tous les handlers sont encapsulés dans une définition SQL via CREATE PROCEDURE.

6. Outils utilisables pour créer/administrer des Stored Procedures

Snowflake documente plusieurs possibilités : [docs.snowflake.com]

  • SQL direct (Snowsight, SnowSQL, worksheets)
  • Snowpark API (Java / Python / Scala)
  • Snowflake CLI
  • Snowflake Python API
  • Snowflake REST API

7. Fonctionnement d'une Stored Procedure

Selon la documentation : [docs.snowflake.com]

  • L'utilisateur exécute CALL my_proc(...)
  • Snowflake invoque le handler (Java/Python/JS…) en lui passant les arguments
  • Le handler exécute la logique
  • Le résultat (ou rien) est renvoyé

Certaines procédures peuvent également retourner un résultat tabulaire selon le langage.

8. Avantages des Stored Procedures

  • Automatisation — idéal pour les pipelines ETL/ELT avancés
  • Réutilisation — logique centralisée dans un objet maintenable
  • Encapsulation — masque la complexité aux utilisateurs finaux
  • Sécurité — owner's rights pour limiter les privilèges directs [docs.snowflake.com]

9. Résumé

Les stored procedures dans Snowflake sont un outil puissant pour automatiser, orchestrer et sécuriser l'exécution de tâches complexes. Comprendre leurs caractéristiques, leurs différences avec les UDF et leur modèle de privilèges est essentiel pour réussir la certification SnowPro Core.
