📌 Micro‑partitions & Table Design Considerations

Voici une synthèse de révision complète, basée exclusivement sur la documentation Snowflake concernant :

  • 📌 Micro‑partitions
  • 📌 Tables – Design Considerations

Sources officielles :

  • Micro‑partitions : [docs.snowflake.com]

Note importante :

Cette thématique est cruciale pour la certification SnowPro Core, car elle touche directement les fondements de performance, stockage, clustering et gestion physique des données dans Snowflake.

✅ 1. Micro‑partitions — Concept clé de Snowflake

🔹 Définition

Snowflake stocke toutes les données des tables sous forme de micro‑partitions, qui sont :

  • des unités de stockage contiguës,
  • contenant 50 à 500 MB de données non compressées,
  • organisées en format colonne.

La taille réelle est plus petite car Snowflake stocke toujours les données compressées.

🔹 Caractéristiques

  • Chaque micro‑partition regroupe un ensemble de lignes mappées à la volée.
  • Stocke des métadonnées riches : ranges de colonnes, NDV, min/max, etc.

[docs.snowflake.com]

🔹 Micro‑partitionnement automatique

  • Aucun partitionnement manuel n'est nécessaire.
  • Snowflake crée les micro‑partitions selon l'ordre d'ingestion.
  • Il n'existe pas de partition statique telle que dans les systèmes traditionnels (Hadoop, BigQuery ancestral, etc.).

[docs.snowflake.com]

🔹 Bénéfices des micro‑partitions

  • Pruning extrême : Snowflake peut éliminer des millions de micro‑partitions lors des scans grâce aux métadonnées min/max.
  • Prévention du skew : les micro‑partitions peuvent se recouper, limitant les déséquilibres de taille.
  • Stockage colonne : seules les colonnes nécessaires au query scan sont lues.
  • Performances élevées pour les requêtes filtrées, jointures, agrégations.

[docs.snowflake.com]

🔹 Clustering & Micro‑partitions

  • Les micro‑partitions constituent la base du clustering Snowflake.
  • Snowflake organise automatiquement les données mais peut dériver si beaucoup de DML.
  • Pour les tables multi‑téraoctets, on peut définir des clustering keys.

[docs.snowflake.com]

✅ 2. Table Design Considerations

Source : Table design considerations. [docs.snowflake.com]

🔹 A. Choix des types de données

✔ Utiliser les types DATE & TIMESTAMP

Snowflake recommande :

  • DATE / TIMESTAMP plutôt que VARCHAR pour stocker des dates.
  • Performances et stockage plus efficaces.

[docs.snowflake.com]

✔ Référential integrity

  • PK / FK sont informations seulement (non appliquées), sauf pour Hybrid Tables.
  • NOT NULL est réellement appliqué.
  • PK/FK restent utiles pour :
    • BI tools (Power BI, Tableau) → génération auto de joins,
    • join elimination.

[docs.snowflake.com]

🔹 B. Importance des contraintes comme métadonnées

Les contraintes apportent :

  • documentation du modèle,
  • meilleure compréhension des relations,
  • support des outils BI (import FK → joins),
  • optimisation de certaines requêtes (join elimination).

[docs.snowflake.com]

🔹 C. GET_DDL pour documenter les objets

Snowflake permet d'extraire la définition d'un objet avec :

SELECT GET_DDL('TABLE', 'MY_TABLE');

Très utile pour :

  • gouvernance,
  • recréation d'objets,
  • migration.

[docs.snowflake.com]

🔹 D. Best practices générales

  • ✔ Comprendre micro‑partitions & clustering → Optimiser les performances sur gros volumes.
  • ✔ Organiser proprement schemas & databases → Structure logique claire = maintenance facilitée.
  • ✔ Minimiser les colonnes VARCHAR → préférer types natifs → Impact sur compression + performances.

[docs.snowflake.com]

✅ 3. Relation entre Micro‑partitions et Design des Tables

Micro‑partitions influencent directement :

✔ 1. Le scan des données

Grâce aux métadonnées min/max → Snowflake ne lit que les micro‑partitions pertinentes.

✔ 2. Le clustering

Une bonne insertion ordonnée ou l'usage de clustering keys facilite le pruning.

✔ 3. La répartition physique des données

Snowflake réorganise automatiquement les micro‑partitions, mais cela peut se dégrader avec beaucoup de UPDATE/DELETE (tables volumineuses).

✔ 4. Time Travel & Fail-safe

Certaines opérations (ex: défragmentation micro‑partitions) créent de nouvelles micro‑partitions → augmentent temporairement le stockage Time Travel.

[docs.snowflake.com]

🧩 4. À connaître absolument pour SnowPro Core

🔥 Micro‑partitions

  • Automatiques, 50–500MB uncompressed.
  • Pruning très efficace (min/max metadata).
  • Stockage colonne → scans plus rapides.
  • Pas de partitionnement manuel.
  • Base du clustering Snowflake.

🔥 Table Design

  • DATE/TIMESTAMP > VARCHAR.
  • PK/FK non enforce sauf hybrid tables (info only).
  • NOT NULL enforce.
  • Contrôles = métadonnées utiles pour BI et optimisation.
  • GET_DDL indispensable pour documentation.

🎯 Résumé final pour examen SnowPro Core

Thème Ce qu'il faut retenir
