Introduction aux vues (Views)

Les views (vues) sont un objet fondamental dans Snowflake. Elles permettent d'exposer le résultat d'une requête comme s'il s'agissait d'une table, tout en offrant des capacités de sécurisation, d'abstraction et de gestion logique des données.

1. Définition d'une View

Une view est un objet Snowflake dont le contenu correspond au résultat d'une requête SQL définie dans une instruction CREATE VIEW.

Elle peut être utilisée exactement comme une table : joins, sous‑requêtes, projections, etc.

Objectifs principaux :

  • Combiner des données
  • Ségréguer des données par profil métier
  • Protéger des données sensibles

→ Séparation logique selon les rôles d'utilisateurs.

2. Utilisation des Views

Une view peut être utilisée dans :

  • JOINS
  • sous‑requêtes
  • analyses complexes

3. Nommage et qualification

Lors de la création d'une view :

CREATE VIEW v1 AS SELECT ... FROM my_database.my_schema.my_table;

Snowflake autorise :

  • noms totalement qualifiés
  • partiellement qualifiés
  • non qualifiés
Important :

Si le schéma n'est pas précisé dans la définition de la vue, Snowflake suppose que la table source se trouve dans le même schéma que la vue.

→ Évite qu'une vue change de table source selon le schéma actif.

4. Types de Views

1. Non‑materialized views

  • Nom générique : views.
  • Simple définition de requête
  • Résultats recalculés à chaque exécution
  • Pas de stockage physique supplémentaire

2. Materialized views

  • Stockent physiquement le résultat
  • Améliorent les performances sur requêtes répétitives

5. Avantages des Views

✔ Sécurité

Les vues cachent les colonnes non nécessaires, protégeant les données sensibles. (ex : PII masquée via un subset logique)

✔ Abstraction

Elles permettent de présenter une représentation métier indépendante du modèle physique.

✔ Maintenabilité

Les modifications sur la table source peuvent être transparentes pour les utilisateurs finaux.

✔ Lisibilité SQL

Elles factorisent des transformations complexes en un objet unique et documenté.

6. Bonnes pratiques

  • Toujours spécifier le schéma lors de la création des vues → évite les résolutions dynamiques et comportements imprévisibles.
  • Utiliser les vues pour limiter l'accès : sécurisation logique des données.
  • Documenter les vues pour clarifier leur rôle métier.
  • Éviter les cascades de vues trop profondes → complexité et pertes de performance potentielles.
  • Utiliser une materialized view uniquement quand les performances le justifient.

7. Résumé

Concept Point clé
Définition Une vue = requête stockée
Types Non‑materialized et materialized
Sécurité Très utilisée pour la gouvernance des données
Utilisation Presque comme une table
Résolution schéma Si non spécifié, même schéma que la vue
Matérialisation Pas dans les views standard
