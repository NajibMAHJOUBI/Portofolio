Snowflake Performance Query Insights

✅ 1. Query Insights – Comprendre et analyser les performances

Snowsight fournit plusieurs vues pour analyser les performances des requêtes :

✔ Query History

Permet :

  • De surveiller les requêtes individuelles ou groupées.
  • D'accéder aux métriques d'exécution (durée, warehouse utilisé, scans, etc.).
  • D'accéder au Query Profile, qui permet de visualiser chaque étape du plan d'exécution.

✔ Query Profile (rappel essentiel SnowPro)

  • Visualisation DAG des opérateurs (TableScan, Join, Filter, Aggregate…).
  • Analyse des étapes lentes et des volumes traités.

✅ 2. Queries too large to fit in memory

✔ Symptômes (connu dans Snowsight)

  • Message indiquant que la requête dépasse la mémoire disponible sur le cluster.
  • Résultats non affichables dans Snowsight ou nécessitant un résultat limité.

✔ Causes fréquentes

  • Requêtes retournant des ensembles de données massifs.
  • Joints ou agrégations produisant des résultats intermédiaires très volumineux.
  • Absence de filtrage ou d'application de LIMIT.

✔ Solutions recommandées

  • Ajouter des filtres plus sélectifs.
  • Utiliser LIMIT dans Snowsight.
  • Matérialiser des résultats intermédiaires dans une table.
  • Revoir le design (cluster key / partitionnement logique).

✅ 3. Clustering, Micro-partitions & Query Pruning

✔ Snowflake Micro-partitions

Snowflake stocke les données en micropartitions columstore de ~50–500 MB compressés chacune.

Chaque micropartition contient des metadata ranges par colonne, permettant de déterminer si elle contient potentiellement les valeurs recherchées.

✔ Query Pruning (pruning efficace)

Le moteur Snowflake identifie quelles micropartitions sont non pertinentes et les ignore.

Cela réduit la quantité de données scannées, et accélère les requêtes. (explication via Query Plan & TableScan)

✔ Inefficient Pruning (détection Snowsight)

Snowsight signale qu'une requête a un pruning inefficace lorsque :

  • Les filtres ne sont pas sélectifs
  • Les prédicats ne peuvent pas utiliser les ranges de micropartitions
  • Les colonnes filtrées ne sont pas corrélées au tri des micropartitions

✔ Causes possibles d'inefficient pruning

  • Filtre sur une expression (ex: WHERE DATE(timestamp_col) = ...)
  • Filtre sur colonne sans corrélation logique avec l'ordre d'insertion
  • Données fortement skew (valeurs similaires, absence de distribution)
✔ Solutions clés (tested SnowPro patterns)
  • Utiliser des prédicats SARGables : timestamp_col >= '2025-01-01' AND timestamp_col < '2025-01-02'
  • Créer un clustering manuel si nécessaire.
  • Chercher à réduire le nombre de micropartitions touchées.

✅ 4. Warehouse Queueing : Query queuing & Concurrency

Queueing se produit lorsque :

✔ Congestion du warehouse

Un warehouse est saturé si :

  • Le nombre de requêtes simultanées dépasse sa capacité.
  • Des tâches lourdes monopolisent les clusters.

✔ Résultats visibles

  • Requêtes en attente dans Snowsight, affichées comme "Queued".
  • Délai avant exécution.

✔ Solutions

  • Augmenter la taille du warehouse (implique plus de compute).
  • Activer multi-cluster pour élasticité.
  • Utiliser des warehouses séparés selon les workloads.

✅ 5. EXPLAIN : Obtenir le plan d'exécution optimisé

✔ Syntaxe

EXPLAIN USING TEXT <query>;

✔ Ce qu'affiche EXPLAIN

  • Le plan logique optimisé, pas l'exécution réelle.
  • Operators : TableScan, Filter, Join, Aggregate, Sort, Result.
  • Informations sur :
    • L'ordre d'exécution
    • Les stratégies de join
    • Les filtres utilisés
    • L'élimination possible via pruning
