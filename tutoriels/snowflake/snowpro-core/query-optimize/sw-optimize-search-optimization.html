Snowflake - Search Optimization Service (SOS)

Niveau Intermédiaire
Mis à jour: Février 2026 Durée: 20 min Difficulté: Intermédiaire
Snowflake SOS Performance

✅ 1. Définition & Objectif du Search Optimization Service

Le Search Optimization Service (SOS) est une fonctionnalité Enterprise Edition (ou supérieure) conçue pour accélérer significativement certaines catégories de requêtes ayant des filtres sélectifs ou des conditions complexes.

✔ But principal

Réduire le nombre de micropartitions analysées et accélérer les recherches sélectives, notamment lorsque le pruning naturel de Snowflake n'est pas suffisant.

✔ Fonctionnement général

SOS crée et maintient une structure spécialisée appelée Search Access Path, permettant de localiser efficacement les partitions contenant les valeurs recherchées.

✅ 2. Types de requêtes qui bénéficient du SOS

La documentation liste précisément les catégories optimisées :

✔ 1. Point Lookups (lookup très sélectif)

Requêtes retournant 1 ou très peu de lignes.

Exemples :

  • Dashboards critiques avec filtres très sélectifs
  • Analyse exploratoire par data scientists
  • Recherche très ciblée dans des grandes tables

✔ 2. Requêtes TEXT & IP

Accélération des recherches utilisant :

  • SEARCH()
  • SEARCH_IP()

✔ 3. Substring & Regex

Optimisation des recherches utilisant :

  • LIKE, ILIKE, RLIKE

✔ 4. Colonnes semi-structurées (VARIANT, OBJECT, ARRAY)

Support des prédicats sur les champs imbriqués, incluant :

  • Comparaisons (=, IN)
  • ARRAY_CONTAINS, ARRAYS_OVERLAP
  • Recherche textuelle dans les champs JSON
  • Vérification de NULL

✔ 5. Colonnes structurées ARRAY / OBJECT / MAP

Optimisation pour :

  • EQUALITY, IN
  • SUBSTRING sur champs STRING

✔ 6. Fonctions géospatiales

Certaines requêtes géospatiales utilisant des données GEOGRAPHY.

✅ 3. Activation du Search Optimization Service

Pour rendre un tableau "search-optimized", il faut utiliser :

ALTER TABLE … ADD SEARCH OPTIMIZATION

✔ Privilèges nécessaires

  • OWNERSHIP sur la table
  • ADD SEARCH OPTIMIZATION sur le schéma

✔ Deux modes d'activation

🟦 1. Activation pour toute la table

Optimise toutes les colonnes supportées → utile pour des point lookups globaux.

ALTER TABLE ma_table ADD SEARCH OPTIMIZATION;

🟦 2. Activation ciblée par colonne(s)

Permet d'économiser des coûts en ciblant uniquement les colonnes critiques :

ALTER TABLE ma_table
    ADD SEARCH OPTIMIZATION ON (col1, col2);

Possibilité de préciser le type de recherche :

  • EQUALITY
  • SUBSTRING
  • GEO

✅ 4. Impact sur les coûts

L'activation du SOS entraîne un coût supplémentaire en compute et stockage.

✔ Coûts de stockage

Le Search Access Path :

  • Peut peser jusqu'à 1/4 de la taille de la table, parfois plus
  • Peut atteindre la taille de la table si toutes les valeurs sont uniques

✔ Coûts compute

Engendrés par :

  • La construction initiale des search paths
  • Le maintien à jour (fort impact si high churn)
  • DELETE/INSERT massifs

✔ Estimation des coûts

Snowflake fournit une fonction :

SYSTEM$ESTIMATE_SEARCH_OPTIMIZATION_COSTS()

→ utile pour évaluer l'impact avant activation

✔ Recommandation Snowflake
→ Commencer par un petit nombre de tables et surveiller les coûts

✅ 5. Maintenance & comportements spécifiques

  • Reconstruction des paths : Si les valeurs par défaut changent, le Search Access Path devient invalidé et doit être recréé.
  • Ajout / suppression / renommage de colonnes :
    • Ajout : pris en compte automatiquement si SOS est activé globalement
    • Suppression : le path est automatiquement mis à jour
    • Renommage : pas de changement nécessaire
  • Clonage : Les clones zéro‑copy incluent aussi les access paths.

✅ 6. Cas où SOS n'est pas recommandé

  • Tables avec high churn (maintenance coûteuse)
  • Tables massives rarement interrogées avec forte sélectivité
  • Tables souvent reconstruites / remplacées (coût de maintenance excessif)

✅ 8. Conclusion

Le Search Optimization Service est un accélérateur puissant pour les requêtes très sélectives ou complexes, particulièrement dans des tables volumineuses. C'est un sujet fréquent en SnowPro Core, notamment dans les domaines :

  • Architecture Snowflake (micro-partitions, pruning)
  • Performance & optimization
  • Coûts & serverless features
  • Table design
