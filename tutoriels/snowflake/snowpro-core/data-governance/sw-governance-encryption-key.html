1. Encryption in Snowflake – Vue d'ensemble

Snowflake applique une stratégie de chiffrement systématique (always‑on encryption). Toutes les données — en transit et au repos — sont chiffrées par défaut, sans intervention de l'utilisateur.

Le thème couvre deux mécanismes clés pour le SnowPro Core :

  • Client‑Side Encryption (CSE) et gestion des clés côté client
  • Tri‑Secret Secure (TSS) : modèle de chiffrement avancé combinant clés Snowflake + clés client

2. Client‑Side Encryption (CSE)

(Security → Encryption → Client‑managed keys)

✔ 2.1. Principe

  • Avec le client‑side encryption, les données sont chiffrées avant d'entrer dans Snowflake.
  • Cela permet aux clients de contrôler leur propre clé de chiffrement externe.
  • La gestion est entièrement côté client :
    • Le client génère les clés,
    • Le client chiffre les données localement,
    • Snowflake ne voit jamais la donnée en clair ni la clé de chiffrement.

✔ 2.2. Cas d'usage

  • Conformité stricte (finance, santé…)
  • Besoin de contrôler totalement la chaîne cryptographique
  • Protection contre fuite accidentelle de données même si un objet Snowflake est compromis
✔ 2.3. Limitations
  • Snowflake ne peut pas opérer sur la donnée en clair (pas de recherche, tri, agrégation…).
  • Le client doit gérer :
    • rotation des clés,
    • stockage sécurisé,
    • gestion de la disponibilité des clés.

3. Snowflake‑Managed Encryption (par défaut)

Même sans CSE ou TSS, Snowflake applique :

✔ Chiffrement en transit

  • TLS 1.2 ou supérieur
  • Communications entre compute, storage et clients sécurisées

✔ Chiffrement au repos

  • Toutes les données sont chiffrées automatiquement dans le cloud storage sous‑jacent
  • Snowflake utilise des keys per object avec rotation automatique

✔ Hiérarchie de clés Snowflake (KMS interne)

Snowflake applique une encryption key hierarchy en trois niveaux :

  • Master Key
  • Database Key / Table Key / Stage Key
  • File Key

Chaque couche protège la clé de la couche inférieure.

4. Tri‑Secret Secure (TSS)

(Thème principal de la certification SnowPro Core)

✔ 4.1. Définition

Tri‑Secret Secure est le mécanisme Snowflake permettant au client de contrôler une partie du chiffrement tout en conservant l'élasticité du service Snowflake.

Il combine :

  • Une clé Snowflake
  • Une clé client stockée sur un service KMS externe (AWS KMS, Azure Key Vault, GCP KMS)
  • La donnée n'est lisible que lorsque les deux clés sont disponibles.

✔ 4.2. Mécanisme à « trois secrets »

  • Secret 1 : la clé maître Snowflake (rotée automatiquement)
  • Secret 2 : la clé client (Customer‑Managed Key)
  • Secret 3 : la combinaison cryptographique (Wrapped DEK) utilisée pour chiffrer les données

→ D'où le nom « Tri‑Secret ».

✔ 4.3. Avantages

  • Contrôle accru : votre clé = votre contrôle
  • Snowflake ne peut pas déchiffrer les données si la clé client est invalidée
  • Rotation synchronisée des clés
  • Conformité renforcée
  • Fonctionne sans impacter les performances (Snowflake interagit avec la clé via KMS)

✔ 4.4. Fonctionnement

  1. Snowflake chiffre la donnée avec une DEK (Data Encryption Key)
  2. La DEK est chiffrée avec la clé Snowflake ET la clé du client
  3. Pour déchiffrer la donnée, Snowflake doit :
    • présenter sa clé,
    • demander l'accès à la clé du client via KMS,
    • reconstruire la DEK,
    • déchiffrer la donnée.
Si le client désactive sa clé → Snowflake ne peut plus lire les données.
C'est un mécanisme de cryptographic kill switch.

6. Points clés à retenir pour SnowPro Core

✔ 1. Tout est chiffré par défaut dans Snowflake

(tant en transit qu'au repos)

✔ 2. Le client peut activer :

  • CSE pour chiffrer AVANT Snowflake
  • TSS pour co‑gérer les clés avec Snowflake

✔ 3. Tri‑Secret Secure

  • Combine trois secrets cryptographiques
  • Nécessite un KMS externe
  • Permet un kill switch via la clé client

✔ 4. Conséquences opérationnelles

  • Pas d'impact sur les performances avec TSS
  • Impact majeur avec CSE (SQL limité)

7. Résumé express (à mémoriser rapidement)

  • Snowflake chiffre tout en natif.
  • Client‑Side Encryption : data chiffrée avant Snowflake, opérations SQL limitées.
  • Tri‑Secret Secure : clé Snowflake + clé client → contrôle total + SQL full.
  • Snowflake utilise une key hierarchy interne avec rotation automatique.
  • Le client peut désactiver sa clé pour bloquer l'accès → kill switch.
