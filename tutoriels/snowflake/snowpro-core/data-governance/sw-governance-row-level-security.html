1. Row-Level Security (RLS) dans Snowflake – Introduction

La Row-Level Security dans Snowflake permet de contrôler quelles lignes d'un tableau ou d'une vue sont visibles pour un utilisateur, une session ou un rôle donné.

Ce mécanisme utilise des Row Access Policies.

❗ Cette fonctionnalité est réservée à Enterprise Edition ou supérieur.

2. Qu'est‑ce qu'une Row Access Policy ?

Une Row Access Policy est un objet de schéma qui :

  • Détermine si une ligne donnée peut être retournée dans une requête.
  • S'applique à :
    • SELECT
    • Les lignes lues durant UPDATE / DELETE / MERGE
  • Peut être attachée à plusieurs tables ou vues simultanément.
  • S'applique à l'exécution, sans modifier les données stockées (même principe que le masking).
  • Elle peut inclure :
    • Des conditions simples (par rôle).
    • Des conditions complexes utilisant des mapping tables.
    • Des context functions (CURRENT_ROLE(), SESSION_USER(), etc.).

3. Comment fonctionne une Row Access Policy ?

Snowflake évalue une Row Access Policy ainsi :

  • La politique renvoie TRUE (ligne visible) ou FALSE (ligne filtrée).
  • L'expression de la politique peut référencer :
    • des fonctions conditionnelles,
    • des fonctions de contexte (ex. IS_DATABASE_ROLE_IN_SESSION()),
    • des objets Snowflake (table de mapping).
Évaluation avec le rôle du policy owner, pas avec le rôle de l'utilisateur exécutant la requête.
➜ Cela permet au policy owner d'accéder aux mapping tables, même si l'utilisateur ne peut pas les voir.

4. Mapping Table (Table d'entitlements)

Pour les politiques complexes (ex : filtrage multi‑régions), Snowflake recommande :

  • De créer une mapping table centralisée.
  • De la stocker dans la même database que la table protégée.
  • Obligatoire si la politique utilise IS_DATABASE_ROLE_IN_SESSION.

Cette table contient les droits d'accès par rôle, ex. :

REGION      | ROLE_ALLOWED
------------|-------------
FR          | ROLE_FRANCE
US          | ROLE_USA

5. Application d'une Row Access Policy

La politique peut être appliquée :

✔ Lors de la création d'une table / vue

CREATE TABLE sales (...)
    WITH ROW ACCESS POLICY rls_sales;

✔ Après la création

ALTER TABLE sales ADD ROW ACCESS POLICY rls_sales;

✔ Retrait de la politique

ALTER TABLE sales DROP ROW ACCESS POLICY rls_sales;

6. Limitations importantes

  • RLS ne bloque pas :
    • l'insertion de lignes,
    • la modification ou suppression de lignes visibles selon la politique.
  • Les messages d'erreur liés aux RLS peuvent être redactés pour protection.
  • Les politiques s'appliquent uniquement à l'accès, pas aux métadonnées.

7. Scénarios où la RLS est indispensable

  • Multi‑tenant (chaque client voit uniquement ses données)
  • Filtrage par région / pays
  • Sécurité interne (salaire, équipes, département)
  • Contraintes réglementaires (GDPR, HIPAA…)

8. Architecture recommandée (3 couches de sécurité)

D'après l'organisation décrite dans la doc et la pratique Snowflake :

  1. RBAC Object Access → a-t-on accès à la table ?
  2. Column-Level Security → que voit-on dans les colonnes ?
  3. Row-Level Security → quelles lignes voit-on ?

9. Exemple conceptuel de Row Access Policy

1. Table de mapping

CREATE TABLE region_entitlements(
    region STRING,
    role_name STRING
);

2. Politique

CREATE ROW ACCESS POLICY rls_sales
AS (region STRING) RETURNS BOOLEAN ->
    EXISTS (
        SELECT 1
        FROM region_entitlements
        WHERE region_entitlements.region = region
            AND IS_ROLE_IN_SESSION(role_name)
    );

3. Application

ALTER TABLE sales ADD ROW ACCESS POLICY rls_sales;

10. Points clés SnowPro Core à retenir

✔ Row-Level Security

  • Se met en place via des Row Access Policies.
  • Fonctionne à l'exécution (runtime).
  • Filtre les lignes sans altérer les données.
  • Peut être simple ou reposer sur une table de mapping.
  • S'applique à toutes les opérations lisant des lignes (SELECT, MERGE…).

✔ Architecture

  • Intégrée avec RBAC / Column Masking pour une sécurité complète.

✔ Technique

  • Politique évaluée avec le rôle du policy owner.
  • Mapping table dans la même database.
  • Une policy peut être appliquée à plusieurs objets.
