Architecture Snowflake - Virtual Warehouses

Niveau Débutant
Mis à jour: Février 2026 Durée: 25 min Difficulté: Intermédiaire
Snowflake Data Engineering Cloud

Objectifs du tutoriel

Ce tutoriel présente les Virtual Warehouses Snowflake, leur fonctionnement, leurs types, tailles, propriétés et les bonnes pratiques pour optimiser leurs coûts et performances.

1. Définition d'un Virtual Warehouse

Un Virtual Warehouse est un cluster de compute utilisé pour :

  • Exécuter des requêtes SQL (SELECT)
  • Effectuer des opérations DML (INSERT, UPDATE, DELETE)
  • Charger des données (COPY INTO)
  • Décharger des données (COPY INTO)
  • Il fournit CPU + RAM + stockage temporaire.
  • Il doit être en cours d'exécution pour que la session puisse l'utiliser.
  • Il consomme des crédits Snowflake tant qu'il est actif.

2. Types de Warehouses

1️⃣ Standard Warehouse

  • Type par défaut.
  • Optimisé pour la majorité des workloads analytiques.

2️⃣ Snowpark-Optimized Warehouse

  • Optimisé pour :
    • Snowpark ML
    • UDFs/UDTFs lourdes
    • Workloads nécessitant beaucoup de CPU
  • Plus coûteux mais plus performant pour les workloads compute‑intensifs.

3. Tailles des Warehouses

Snowflake propose plusieurs tailles :

Taille Description
X-Small Taille par défaut
Small → 6X-Large Augmentation progressive du compute
Multi-cluster Plusieurs clusters pour absorber la concurrence
  • La taille détermine la puissance de calcul par cluster.
  • Les warehouses peuvent être redimensionnés à chaud, même en cours d'exécution.

4. Multi‑Cluster Warehouses

  • Permettent d'ajouter automatiquement des clusters supplémentaires pour gérer la concurrence élevée.
  • Modes :
    • Auto-scale (min/max clusters)
    • Maximiser la disponibilité ou minimiser les coûts
  • Snowflake démarre/arrête les clusters selon la charge.

5. Propriétés importantes d'un Warehouse

🛑 Auto-Suspend

  • Arrête automatiquement le Warehouse après une période d'inactivité.
  • Permet d'économiser des crédits.

▶️ Auto-Resume

  • Redémarre automatiquement le Warehouse lorsqu'une requête arrive.

🔁 Scaling Policy

  • Standard : équilibre entre performance et coût.
  • Economy : limite le scaling pour réduire les coûts.

🧹 Query Result Caching

  • Les résultats mis en cache peuvent être renvoyés sans consommer de compute.

6. Gen1 vs Gen2 Warehouses

Snowflake propose des Warehouses de nouvelle génération (Gen2) :

  • meilleures performances,
  • meilleure gestion des DELETE/UPDATE/MERGE,
  • scans plus rapides.

7. Facturation

🔹 Les crédits dépendent de :

  • la taille du warehouse,
  • le nombre de clusters (si multi‑cluster),
  • le temps d'exécution.

🔹 Règles de facturation

  • Minimum 60 secondes à chaque démarrage.
  • Ensuite facturation à la seconde.
  • Si un warehouse démarre, s'arrête puis redémarre sans dépasser 60s → nouveau minimum de 60s.

🔹 Redimensionnement (resizing)

Changer la taille d'un Warehouse :

  • Provisionne des nouvelles ressources,
  • entraîne un surcoût au moment du provisionnement.

8. Query Acceleration Service (QAS)

Service optionnel pour accélérer :

  • les requêtes lentes ou atypiques,
  • les charges analytiques irrégulières.

QAS ajoute du compute supplémentaire sans redimensionner le Warehouse.

9. Bonnes pratiques

✔ Ne pas se focaliser uniquement sur la taille

Avec la facturation à la seconde, utiliser un Warehouse large pendant peu de temps peut être moins coûteux qu'un petit qui reste actif plus longtemps.

✔ Suspendre les warehouses inactifs

Toujours activer AUTO-SUSPEND et AUTO-RESUME.

✔ Tester les tailles pour déterminer le meilleur rapport coût/performance

Les workloads varient, donc Snowflake recommande de tester.

✔ Utiliser le multi‑cluster pour gérer la concurrence

Pour éviter que des requêtes restent en file d'attente.
