Architecture Snowflake - Stockage des données

Niveau Débutant
Mis à jour: Février 2026 Durée: 10 min Difficulté: Intermédiaire
Microsoft Fabric Data Engineering Cloud

Objectifs du tutoriel

Snowflake n'offre pas un seul modèle de table, mais plusieurs, chacun répondant à des cas d'usage spécifiques.

Que vous soyez architecte de données, ingénieur data ou analyste avancé, comprendre les nuances entre les différents types de tables Snowflake est devenu indispensable pour :

  • Optimiser les performances en adaptant la structure de stockage à la nature de vos requêtes
  • Maîtriser les coûts en choisissant la solution la plus économique pour chaque cas d'usage
  • Garantir la fraîcheur des données avec des modèles adaptés aux besoins transactionnels ou analytiques
  • Éviter le verrouillage propriétaire en adoptant des formats ouverts comme Iceberg

Les trois piliers du stockage Snowflake

Dans ce tutoriel, nous allons explorer en profondeur les trois principaux types de tables que Snowflake met à votre disposition :
Type de table Architecture
Tables standard (Micro-partitions) Stockage propriétaire Snowflake
Tables Iceberg Format ouvert (Apache Iceberg)
Tables hybrides Stockage transactionnel optimisé

Au fil de ce guide pratique, nous allons :

  • Décortiquer l'architecture des micro-partitions : Comprendre pourquoi et comment Snowflake découpe automatiquement vos données, et comment exploiter cette architecture pour des requêtes ultra-rapides sans indexation manuelle.
  • Explorer les tables Iceberg : Découvrir comment Snowflake s'ouvre aux formats de données ouverts pour permettre de gérer vos données là où elles résident, sans duplication, tout en bénéficiant de la puissance de calcul Snowflake.
  • Maîtriser les tables hybrides : Plonger dans cette innovation récente qui bouscule les frontières traditionnelles entre les bases de données transactionnelles (OLTP) et analytiques (OLAP), en offrant des performances de type ligne sur des données volumineuses.
  • Comparer et choisir : À travers un scénario concret, nous mettrons en œuvre chaque type de table sur un même jeu de données pour illustrer leurs forces et faiblesses respectives.

Snowflake tables - Micro‑partitions

🧊 1. Définition d’une micro‑partition

  • Unité physique fondamentale de stockage dans Snowflake.
  • Chaque table est découpée automatiquement en micro‑partitions contiguës, immuables et colonne‑orientées.
  • Taille typique : 50 à 500 Mo de données compressées.
  • Snowflake gère automatiquement leur création, leur organisation et leur maintenance.

📦 2. Caractéristiques essentielles

🧱 Structure

  • Stockage en colonnes → compression élevée + lecture sélective.
  • Chaque micro‑partition contient :
    • Les données des colonnes
    • Des métadonnées riches (min/max, cardinalité, null-count, bloom filters…)

🔒 Immutabilité

  • Une fois écrite, une micro‑partition n’est jamais modifiée.
  • Toute modification (INSERT/UPDATE/DELETE) crée de nouvelles micro‑partitions.
  • Les anciennes sont marquées comme inactives → Time Travel & Fail-safe.

🧭 Métadonnées

  • Snowflake stocke automatiquement :
    • Min/max par colonne
    • Nombre de valeurs NULL
    • Histogrammes légers
    • Informations de clustering
  • Ces métadonnées permettent un pruning très efficace.

✂️ 3. Micro‑partition pruning (élimination)

Le pruning est un mécanisme clé pour la performance.

🎯 Objectif

Éviter de scanner les micro‑partitions qui ne contiennent pas les données pertinentes.

🔍 Fonctionnement

  • Snowflake compare les prédicats de la requête (WHERE) avec les métadonnées min/max.
  • Si une micro‑partition ne peut pas contenir les valeurs recherchées → elle est ignorée.

🧠 Essentiel

  • Le pruning est automatique.
  • Il dépend fortement de la distribution naturelle des données.
  • Les clustering keys peuvent améliorer le pruning pour les très grandes tables.

🧩 4. Clustering et micro‑partitions

🌱 Clustering naturel

  • Snowflake organise les micro‑partitions selon l’ordre d’ingestion.
  • Pour la majorité des tables, cela suffit.

🌳 Clustering explicite (Clustering Keys)

  • Utile pour les tables multi‑téraoctets.
  • Permet d’améliorer le pruning en regroupant les valeurs similaires dans les mêmes micro‑partitions.
  • Snowflake propose :
    • Automatic Clustering (recommandé)
    • Manual Reclustering (déprécié)

Snowflake tables - Apache Iceberg Tables

🧊 1. Qu’est‑ce qu’une Iceberg Table dans Snowflake ?

  • Type de table permettant d’utiliser le format ouvert Apache Iceberg tout en bénéficiant du moteur Snowflake.
  • Idéale pour les data lakes existants que l’on ne souhaite pas migrer dans Snowflake.
  • Supporte : ACID Schema evolution Hidden partitioning Snapshots
  • Snowflake lit/écrit des fichiers Parquet stockés dans un cloud storage externe (S3, GCS, Azure Blob).

📦 2. Architecture & Stockage

📁 Données stockées hors Snowflake

  • Les fichiers (data + metadata) sont dans un external cloud storage.
  • Snowflake n’applique de Fail-safe aux Iceberg tables.
  • Aucun coût de stockage Snowflake → facturation par le cloud provider.

🔗 External Volume

  • Objet Snowflake permettant de connecter Snowflake au stockage externe.
  • Contient les credentials IAM nécessaires.
  • Un même external volume peut servir plusieurs tables.

📚 3. Catalogues Iceberg

Deux options :

Option Description Avantages Limitations
Snowflake as Catalog Snowflake gère le catalogue Iceberg Support complet Snowflake, DDL/DML, maintenance automatique Toujours external storage
External Catalog (Glue, REST, Open Catalog...) Snowflake lit le catalogue externe via une catalog integration Interopérabilité avec autres moteurs Support Snowflake limité, pas de clustering

🧩 4. Métadonnées & Snapshots

  • Iceberg utilise un modèle basé sur les snapshots.
  • Chaque snapshot référence un ensemble de fichiers (manifests + data files).
  • Snowflake peut lire n’importe quel snapshot compatible.
  • Time Travel possible si la table est rafraîchie régulièrement (pour les tables externes).

🔄 5. Types de tables Iceberg dans Snowflake

1️⃣ Snowflake‑managed Iceberg Table

  • Snowflake = catalog
  • Snowflake gère :
    • Compaction
    • Maintenance
    • DDL/DML complets
  • Supporte clustering keys
  • Recommandé pour un usage Snowflake‑first

2️⃣ Externally‑managed Iceberg Table

  • Catalog externe (Glue, REST, Open Catalog…)
  • Snowflake peut :
    • Lire
    • Écrire (selon version Iceberg)
  • Snowflake ne gère pas la maintenance
  • Pas de clustering
  • Nécessite des refresh manuels/automatisés

⚙️ 6. DML, Maintenance & Limitations

✏️ DML

  • Snowflake supporte INSERT/UPDATE/DELETE selon :
    • Version Iceberg (v2/v3)
    • Type de table (Snowflake‑managed vs external)
  • Row‑level deletes :
    • Position deletes (v2)
    • Deletion vectors (v3)

🧹 Maintenance

  • Snowflake‑managed : compaction automatique
  • Externally‑managed : maintenance via moteur externe (Spark, Flink…)

🌍 7. Cross‑Cloud / Cross‑Region

  • Snowflake peut accéder à un external volume dans un autre cloud ou une autre région.
  • Cela entraîne des egress costs côté cloud provider.
  • Snowflake facture les data transfer pour les tables Snowflake‑managed cross‑region.

💰 8. Billing

Snowflake facture :

  • Compute (warehouses)
  • Cloud services /li>
  • Automated refresh
  • Data transfer (si cross‑region)

Snowflake ne facture pas :

  • Le stockage des Iceberg tables (facturé par le cloud provider)
  • Les active bytes (affichés pour information)

Snowflake tables -Hybrid Tables

⭐ 1. Définition & Objectif

  • Une Hybrid Table est un type de table Snowflake conçu pour les workloads transactionnels (OLTP) à faible latence et haut débit.
  • Elle combine :
    • Stockage orienté lignes (row-based)
    • Indexation pour accès aléatoire rapide
    • Verrouillage de lignes (row-level locking)
    • Contraintes d’unicité et d’intégrité référentielle
  • Permet d’exécuter OLTP + OLAP sur la même plateforme → cœur de Unistore.

⚙️ 2. Caractéristiques techniques essentielles

🧱 Moteur de stockage

  • Stockage row-based, contrairement aux tables Snowflake classiques (columnar).
  • Optimisé pour :
    • Petites lectures/écritures fréquentes
    • Accès aléatoire
    • Haute concurrence

🔍 Indexation

  • Utilise des indexes internes pour accélérer les recherches.
  • Snowflake gère automatiquement la structure d’index.

🔒 Concurrence & Verrouillage

  • Support du row-level locking → essentiel pour les transactions simultanées.
  • Permet des scénarios avec forte concurrence (ex. workflows d’ingestion, applications transactionnelles).

🧩 Contraintes

  • Supporte :
    • PRIMARY KEY
    • UNIQUE
    • FOREIGN KEY
  • Contraintes enforcées, contrairement aux tables classiques.

🧪 3. Cas d’usage typiques

  • Métadonnées d’applications (état de workflow, sessions, tokens…).
  • Applications nécessitant :
    • Beaucoup de petites mises à jour
    • Des lectures rapides par clé
    • Des contraintes d’intégrité strictes
  • Workloads Unistore combinant transactions + analytics.

🏗️ 4. Création & Gestion

🛠️ Création 

CREATE HYBRID TABLE my_table ( 
  id INT PRIMARY KEY, 
  value STRING, 
  updated_at TIMESTAMP 
);

🔄 DML

  • INSERT, UPDATE, DELETE → optimisés pour les opérations ligne par ligne.
  • Transactions ACID complètes.

🧹 Maintenance

  • Snowflake gère automatiquement :
    • Indexes
    • Stockage
    • Concurrence

📊 5. Comparaison : Hybrid Tables vs Tables classiques

Caractéristiques Hybrid Table Table Snowflake - Micro-partitions
Stockage Row-based Columnar
Index Oui Non
Verouillage Row-level Micro-partitions immuables
Contraintes PK/FK Enforcées Non-enforcées
Workloads OLTP + Unistore OLAP
Latence Très faible Optimisée pour scans massifs
Pruning Non applicable Basé sur micro-partitions

📊 5. Comparaison : Hybrid Tables vs Tables classiques

  • Disponible uniquement dans les régions AWS et Azure commerciales.
  • Pas encore disponible sur GCP.
  • Certaines fonctionnalités avancées Snowflake (ex. clustering keys) ne s’appliquent pas.
  • Pas de micro-partitions → pas de pruning basé sur min/max.
